## 从你的目标开始

| 你想做什么 | 从哪里进入 | 你能得到什么 |
|---|---|---|
| 写长篇小说、网文或系列故事 | 新建 → 长篇小说 | 从设定、角色、卷章大纲到正文，并持续管理伏笔、事实和角色状态 |
| 完成一篇结构紧凑的故事 | 新建 → 短篇小说 | 故事设计、章节卡、逐章创作、审校与成稿导出 |
| 把已有小说改成剧本 | 新建 → 小说转剧本 | 来源分析、改编规划、场景写作与 Fountain / FDX / 打印导出 |
| 把已有小说改成漫画 | 新建 → 小说转漫画 | 分页、分镜、角色视觉资料、图像与排字、分镜版或视觉版导出 |
| 搭建可复用的故事世界 | 新建 → 世界引擎 | 独立设定、角色与规则；确认后封存为可引用的世界版本 |
| 自由组合长篇创作步骤 | 节点创作（预览） | 在可视节点中连接资料与生成动作，复用长篇的数据与能力 |
| 先玩一段现成的故事 | 跑团 → 跑团作品（预览） | 《雾港：最后一盏灯》：AI KP、调查、同伴、秘密与结局选择 |
| 制作角色互动或文字游戏 | 角色聊天 / 后日谈小镇 / 文字游戏（预览） | 基于已封存世界制作自己的独立体验，按各产品成熟度试用 |

**只写小说不需要先建立世界引擎。** 长篇和短篇可以在作者确认后派生世界；剧本、漫画有各自独立的改编流程。游玩已提供的跑团作品也不需要先制作世界。

## StoryForge 为创作多做了什么

故事变长后，需要找回很久以前的伏笔；小说变成剧本，需要重新安排冲突与场次；漫画有了漂亮画面，还需要正确的阅读顺序、对白和连续性。StoryForge 围绕这些具体问题，为不同产品建立了各自的生产流程，并共享可追溯、可恢复的 AI 执行底座。

| 产品 | 我们实现的关键设计 | 对使用者的价值 |
|---|---|---|
| 长篇 | 原文、结构化事实、分层摘要与按需检索；章后整理与未来影响分析 | 查回早期依据，让新章节承接人物、伏笔与主支线；修改时看清影响范围 |
| 节点（预览） | 可视节点绑定长篇正式动作，共用作品、记忆与候选采纳链 | 拆开生成步骤、组合中间产物，沿用已有作品继续创作 |
| 短篇 | 独立篇幅与章节合同、逐章确认、带原文证据的审校、成稿检查 | 从一个点子推进到篇幅可控、问题可定位、版本可导出的短篇 |
| 剧本 | 冻结原文来源，关联事实与因果、改编决定、节拍、场景和结构化正文 | 查明每次删改的依据，分别审查原著忠实度与戏剧效果 |
| 漫画 | 脚本到页格的分阶段生产、角色视觉档案、显式阅读链、独立排字层 | 分别调整叙事、画面与对白；重做某一格，并检查整页是否可读 |
| 世界引擎 | 带来源的语义快照、不可变世界版本、按产品需求读取 | 同一个世界可供多个作品引用，每次制作都知道自己用了哪一版设定 |
| 互动产品（预览） | 各自的规则、角色知识、事件、存档与演出状态 | 让行动有可记录的后果，让不同玩家和不同分支拥有独立经历 |

下文按产品展开这些机制、实际入口和当前边界；也可以直接看 [Harness 架构与长期一致性闭环](#共享技术底座)，沿源码和回归测试核对实现。

## 快速开始

### 在线打开

访问 **[StoryForge 在线版](https://yuanbw.vercel.app/storyforge/)**。核心本地创作无需注册 StoryForge 账号；AI 生成需要你配置模型服务。第一次使用可以先手工创建作品、填写设定，再接入 AI。

如在线版与本文界面不同，或模型接口受浏览器跨域限制，请使用下面的本地方式。网站和本地地址拥有各自的浏览器数据，切换前请先导出备份。

### 本地运行

推荐 **Node.js 24**（与 CI 一致）和 npm。Windows、macOS、Linux 都可通过源码运行。

```bash
git clone https://github.com/yuanbw2025/storyforge.git
cd storyforge
npm ci
npm run dev
```

打开终端显示的地址，应用路径为 `/storyforge/`。例如默认端口可用时是 `http://localhost:5173/storyforge/`；端口被占用时以终端输出为准。使用期间保持终端运行，退出时按 `Ctrl+C`。

不使用 Git 也可以[下载最新 main 源码 ZIP](https://github.com/yuanbw2025/storyforge/archive/refs/heads/main.zip)，解压后在项目目录运行 `npm ci` 和 `npm run dev`。

[已发布版本与更新说明](https://github.com/yuanbw2025/storyforge/releases)用于查看固定历史版本。**源码 ZIP 需要上述运行步骤，不是双击安装包。**

### 第一次接入 AI

1. 点击首页右上角 **“模型与本地设置”**，或在长篇工作区左侧进入 **“设置”**。
2. 选择服务商，填写自己的 API Key、Base URL 和模型名称；模型需在你的账户中实际可调用。
3. 使用连接测试检查配置，再以一次小规模生成验证任务效果。连接成功不代表余额、输出长度和所有任务能力都已满足。
4. 出现跨域错误时，按设置页提示使用本地代理。不要把 API Key 填进作品简介、提示词或公开反馈。

详细说明见下方[模型与费用](#模型与费用)。

## 第一次创作

![新建入口：世界、长篇、短篇、剧本和漫画分别创建](./docs/assets/readme/create-work.png)

以长篇为例，你可以这样完成第一轮：

1. **创建作品**：首页点击“新建”，选择“长篇小说”，输入名称与简介。项目文件夹可以稍后设置。
2. **说明想写什么**：在“项目概况”“项目参考”“创作规则”中整理目标、参考和要求。只填这次创作需要的内容，不必先填满全部设定。
3. **建立故事骨架**：在“故事设计”“角色设计”中确定冲突、人物和动机，再进入“大纲”安排卷与章节。可以手写，也可以请求 AI 候选后修改和确认。
4. **写第一章**：进入“章节”，从大纲和细纲推进正文，使用生成、续写或编辑工具。先看候选，再决定是否采纳。
5. **整理后续影响**：检查本章带来的事实、人物状态、关系和伏笔变化，确认需要保留的内容，为下一章准备依据。
6. **带走作品**：进入“数据管理”，用 Markdown / TXT 导出正文，用 JSON 保存完整备份。

截图使用隔离的“灯塔来信 · README 演示”项目与手工填写的大纲，展示真实操作界面，不代表模型生成质量。

## 长篇与节点

### 从设定到正文的分步骤创作

![分步骤长篇：设定导航、卷章结构与可编辑大纲](./docs/assets/readme/longform-outline.png)

长篇工作区把创作过程中需要反复查看的内容放在一起：

| 创作环节 | 主要工具 | 对作者的帮助 |
|---|---|---|
| 构思与资料 | 灵感反推、项目参考、文档解析、资料与检索库 | 把零散想法和参考资料转成后续创作依据 |
| 世界与背景 | 世界起源、自然/人文环境、历史年表、世界地图、重要地点 | 管理作品内部的设定与空间关系 |
| 故事与人物 | 故事设计、主支线、角色生成与档案、关系网、角色驱动 | 让人物动机、冲突和情节规划相互关联 |
| 大纲与写作 | 卷纲、章纲、细纲、章节编辑、续写、扩写、重写、润色 | 在整体规划与逐章写作之间来回调整 |
| 连续性管理 | 伏笔、事实库、状态表、物品栏、故事年表、章后整理 | 跟踪写过的事实与变化，减少长篇中的遗漏和冲突 |
| 风格与控制 | 文风学习、创作规则、提示词库、上下文查看、AI 对话副驾 | 明确自己的写作要求，检查并决定 AI 的输入与结果 |
| 保存与恢复 | 自动保存、版本历史、完整备份、本地记忆工作区 | 保留作品与创作过程，便于备份和继续工作 |

### 长篇记忆：早期线索有依据，后续变化有去向

**为跨章连续性建立四层资料链。** 正文保留原始证据，事实、人物关系、事件与主支线保存结构化状态，章节/卷/全局摘要帮助定位，检索索引负责找回相关片段。生成任务通过 Context Gateway 先查目录、再按需读取细节，并记录实际使用的来源。摘要与索引会核对原文内容指纹；过期或缺失时保留原文回查路径。

例如写到后半部再次出现一件旧物时，检索链可以定位前文记载，再读取原文核对持有者、约定和出现时间。作品作用域与章节时间边界也参与过滤，减少混入其他作品内容或提前泄露后续情节的风险。作者可检查取到了哪些依据、还缺哪些内容。

**为“写完一章之后怎么办”建立确认流程。** 正文采纳后，章后整理提出事实、人物状态、关系、物品、年表、伏笔与主支线等变化候选，再由作者确认。主支线偏差与设定变化进入未来影响分析：已确认历史保持稳定，需要调整的后续规划标记为待处理，作者决定如何修订。

例如你提前揭开了一个秘密，可以检查哪些未来章纲和伏笔安排需要调整，再逐项处理。生成、修改与正式写回都有版本检查；等待确认期间原文发生变化，旧候选会被拦截，避免覆盖刚完成的编辑。

实现入口：[长篇检索](./src/lib/context-gateway/narrative-retrieval.ts)、[章后整理](./src/lib/ai/chapter-memory/run-chapter-memory.ts)、[长篇产品契约与验收边界](./docs/products/LONGFORM-AND-NODE.md)。

长篇已完成当前工程主链与 10 万 / 30 万 / 100 万字符规模验证。它证明数据与检索链路具备工程扩展基础；实际文学质量、长程一致性与费用仍取决于作品、模型和作者审校，不能理解为“一键生成百万字精品”。

### 节点创作：把长篇流程摆在画布上

节点模式用于查看、拆解和组合中间产物：连接资料、生成步骤和后续处理，检查每一步的输入输出。官方节点动作绑定长篇的正式领域 Skill，沿用同一份作品、上下文和候选采纳机制；开发者扩展节点时也沿用这些边界。

这种架构让“标准步骤”与“自由编排”可以共享能力：作者可围绕角色、场景或章节组织更细的工作流，某个正式生成动作的质量改进也能供两种入口复用。实验节点的草稿不能直接采纳为正式作品内容。

当前为**预览**，完整跨模式互操作仍在持续验证。日常写作可从分步骤模式开始，熟悉后再探索节点工作流。

## 短篇、剧本与漫画

三种产品在“新建”中各有入口，拥有自己的作品结构、审校和导出方式。

### 短篇小说

面向 **5,000～25,000 字、3～8 章**的独立故事，为短篇单独实现了创作要求、故事设计、章节规划、正文、全篇审校与定向重写的生产链。

- **把篇幅目标变成完成条件。** 创作要求与故事设计先确认，再逐章生成、编辑和采纳。完成检查读取实际正文长度、章节卡与正文完整性，显示与目标字数的偏差，帮助作者控制短篇规模。
- **让审校意见落到原文。** 问题带有章节和证据，重写针对具体章节；审校记录绑定本次手稿的内容指纹。正文改动后需要重新审校，避免拿旧报告给新稿盖章。
- **保留可交付的定稿。** 缺失章节、待处理候选和未解决的严重问题会阻止发布。通过检查后新增冻结作品版本，后续继续修订可保留原版，导出 **Markdown、TXT、JSON**。

对作者而言，工作台持续回答三个问题：还差哪一章、哪里需要修改、这一版是否已经完成。实现入口：[短篇生产与完成检查](./src/lib/short-novel/service.ts)、[独立 AI 运行链](./src/lib/agent/run/short-novel-durable.ts)。

### 小说转剧本

从本地小说选择来源后，系统冻结本次改编的内容与范围，再把原文组织成可追踪的事实、因果关系和改编决定，逐步推进到节拍、场景卡和场景正文。

- **把改编选择保存成独立资料。** 关键事实、人物动机与因果关系关联原文，删改决定继续关联后面的节拍和场景。作者可以检查一次人物合并或事件删减的依据，再判断是否接受。
- **用结构化剧本组织场景。** 场景正文采用 AST（结构化语法树）表示剧本块，配合场景卡管理动作和对白。格式由代码校验，同一份结构可导出 **Fountain、FDX 或打印版本**，便于继续编剧工作。
- **把忠实度与戏剧性分开审。** 来源忠实度审查和戏剧结构审查分别记录问题；修订补丁指定场景、问题和预期版本。已锁定场景需先解锁，过期修订无法直接写入，作者可以逐场改进而保留其余内容。

例如把小说中的内心独白改成一场对峙，作者可沿来源与场景映射核对信息是否保留，再审查动作、冲突和节奏是否成立。发布时冻结来源、改编决定与场景，后续改小说不会悄悄改变已导出的剧本。

实现入口：[剧本生产与定向修订](./src/lib/screenplay/production.ts)、[版本封存](./src/lib/screenplay/release.ts)、[格式渲染](./src/lib/screenplay/renderers.ts)。

### 小说转漫画

漫画采用分阶段生产：先把小说转成漫画脚本、节拍、分页和页格，再制作视觉素材与排字。作者可以在花费生图费用之前，先检查故事是否适合这样分镜。

- **把阅读顺序写进数据结构。** 页与格有稳定标识、布局和显式阅读链，保存镜头、动作、对白及来源关联。系统检查阅读顺序和页格结构，叙事审查再检查节奏与信息表达，问题可以定位到具体一页或一格。
- **为角色与场景建立视觉档案。** 人物、地点、道具有稳定身份、特征和选定参考素材；图片候选记录服务商、请求与实际参考图传输证据。作者可追踪一张图的来源，并为不合适的格子重新选图或生成。
- **把画面与文字分层制作。** 生图请求为对白区域留空间；气泡、旁白和拟声由本地 SVG 排字层渲染，可独立修改文字、字体和位置。对白错字无需重画整格，检查器会提示文字容量、重叠与边界问题；画面遮挡仍需作者审看。
- **分别交付分镜版与视觉版。** 两种版本有各自的完成检查；视觉版还检查选定图片和实际二进制内容。发布版本保留对图片 Blob 的强引用，避免仅因工作稿换图就丢失旧版媒资；通过对应检查后可导出 **PNG、WebP、CBZ 或 PDF**。

**当前图像接入边界：** 内置通用 OpenAI 兼容图像适配器当前只发送文本，未声明参考图、固定 seed 或局部重绘能力。系统会提示限制，不能把“在提示词中提到参考图”记作已传图的证据。视觉制作需要单独配置图像服务或采用符合要求的作者素材；角色一致性仍需要人工选图与审校。

实现入口：[漫画生产](./src/lib/comic/production.ts)、[媒资与生成证据](./src/lib/comic/media-service.ts)、[本地排字](./src/lib/comic/renderers.ts)、[双版本质量检查](./src/lib/comic/qa.ts)。

以上三个产品已完成当前主干的工程闭环，内容质量和不同服务商的实际效果仍持续评测。各格式的具体适用条件以产品工作台为准。

## 世界与互动体验

世界引擎用于把设定、角色、关系与规则整理成可以被重复引用的世界。你可以从零构建，也可以由长篇或短篇显式派生；封存后，互动产品使用确定的世界版本。

```mermaid
flowchart LR
  A[长篇小说] -->|作者选择派生| W[世界草稿]
  B[短篇小说] -->|作者选择派生| W
  C[从零构建世界] --> W
  W -->|确认并封存| V[世界版本]
  V --> P[在具体产品中配置并开始制作]
  P --> R[发布作品并游玩]
  N[小说来源] --> S[独立剧本改编]
  N --> M[独立漫画改编]
```

小说本身就是完整作品；派生世界是可选的下一步。原作品的后续修改不会自动同步到派生世界，游戏进度也不会自动改写共享世界。

### 世界引擎：让故事资产可以稳定复用

**我们为世界建立了独立身份、来源记录和不可变版本。** 从小说派生时保存作者选定的内容范围、作品版本与内容指纹；封存时只收集设定、人物、关系等语义内容。图片、剧本成品和游戏存档由各产品自己管理。

**不同产品按自己的需要读世界。** 跑团需要规则和秘密，角色聊天需要人物与关系，小镇需要居民和地点。各产品声明必读、选读与禁止读取的内容，在开始制作前冻结来源计划（SourcePlan）；通过 `describe / search / read` 逐步读取，并留下每次读取记录和最终来源清单（SourceManifest）。这些记录把“计划使用什么”和“实际使用了什么”关联起来。

这让作者可以用世界第一版发布一场跑团，同时继续编辑第二版设定。已有游戏仍引用第一版，另一部作品可以明确选择新版本；开发者也能接入新的叙事产品，而无需让它直接遍历世界引擎的内部数据库。

实现入口：[世界版本读取接口](./src/lib/context-gateway/world-release-client.ts)、[世界引擎契约](./docs/products/WORLD-ENGINE.md)。

## 共享技术底座

### 项目架构：独立产品，共享受治理的 AI 执行能力

不同产品有各自的领域服务、章节、场景、页格或运行状态。**Harness 是模型调用外围的执行与校验系统**：它负责记录一次任务的约定、实际输入、候选、版本、检查点与结果，再把这些证据连接到作品数据。

### Harness 如何维护长期一致性

**长期一致性依赖“依据可回查、变化经确认、下一步读到正确版本”的持续循环。** 一章的生成只是其中一次运行；跨章记忆、审校、写回和未来规划共同构成闭环。

```mermaid
flowchart TB
  K["已确认资料<br/>原文 / 事实 / 状态 / 伏笔"]
  K --> R["1. 冻结任务与按需读取<br/>记录作用域、时间、版本与缺失"]
  R --> C["2. 生成并检查候选<br/>结构 / 信息边界 / 按需语义审查"]
  C --> A["3. 作者确认与版本检查<br/>采纳 → 回读 → 验收回执"]
  A --> P["4. 章后整理与未来影响<br/>提出变化 → 作者确认"]
  P -->|"更新资料与索引 · 供后续章节使用"| K
  R -. "必需证据不足" .-> X["暂停 / 拒绝写回<br/>保留证据，等待处理"]
  A -. "来源或目标已过期" .-> X
  classDef engine fill:#e8f0fa,stroke:#5279a4,color:#18324f
  classDef author fill:#fff2df,stroke:#b58a45,color:#593b16
  classDef data fill:#eaf4ee,stroke:#628b73,color:#254a34
  classDef paused fill:#f7eaea,stroke:#b27a7a,color:#6a3030
  class R,C engine
  class A,P author
  class K data
  class X paused
```

每个正式运行另有持久化账本与检查点；章后整理和未来修订由独立、有限的运行承接，也需要各自的版本检查与确认。图中的循环可以跨多次创作会话完成。

| 一致性问题 | Harness 与领域机制如何处理 | 给作者留下的依据 |
|---|---|---|
| 早期事实、伏笔被遗忘 | 结构化事实、分层摘要与长尾检索定位证据，再核对原文；必需来源不足时阻止继续 | Context Manifest 记录来源、内容指纹、实际读取与缺失 |
| 引入错误作品或过早知道后文 | 按作品/世界作用域与任务时间边界过滤来源，并检查信息边界 | 可检查的来源范围与边界证据 |
| 生成期间作者修改了设定 | 采纳前复查关键上下文与目标 revision；旧候选标记 stale，不能直接覆盖 | 候选绑定的输入版本、过期原因与原始输出 |
| 写入成功但后续没有承接 | `adopt()` 后回读实际状态；章后整理连接记忆、检索与故事线，未来影响候选由作者处理 | 写回事件、post-state、后续运行关联与验收回执 |
| 审校结论落后于手稿 | 显式一致性审计绑定正文 hash；正文变化使旧审计凭据失效 | 可恢复的审计候选、所用来源与问题记录 |
| 刷新或中断打断创作链 | 从已验证检查点恢复并复查版本；已保存候选可复用，结果未知的外部请求不盲目重发 | run / attempt / checkpoint 与失败或完成记录 |

例如，第 8 章确定某件信物只能由一人持有，第 80 章又要用到它：检索提供原文和已确认的归属状态，当前任务记录这些依据；如果你在候选生成后改了信物归属，版本检查会阻止旧候选直接采纳。采纳新章后，归属变化再进入章后整理，经确认供后续章节读取。这是机制示例；能否识别所有隐含矛盾，仍取决于审查能力和作者判断。

## 模型与费用

StoryForge 使用你自己的模型服务，API 费用由相应服务商收取。开源代码和本地数据管理不意味着云端生成免费。

| 接入方式 | 设置页提供的选项 |
|---|---|
| 云端文本服务 | DeepSeek、通义千问、豆包、MiniMax、智谱、文心、Kimi、OpenAI、Claude、Gemini 等 |
| 聚合与兼容接口 | Poe、NVIDIA NIM、魔搭等预设，以及自定义 Base URL |
| 本地模型 | Ollama、LM Studio 等本地兼容服务 |
| 图像与其他媒资 | 在具体产品中配置对应 provider；与文本生成能力分别验证 |

这些是当前接入选项，**不是每个模型都已通过所有产品的效果测试**。模型名称、可用额度与能力以服务商账户为准。完整设置实现见 [AIConfigPanel](./src/components/settings/AIConfigPanel.tsx)。

- **提示词可查看与调整**：可使用提示词库、创作规则和补充要求来控制任务。
- **上下文按任务组织**：从作品设定、角色、大纲、正文与记忆等来源选取；可检查上下文和运行证据。
- **费用可观察**：通过消耗统计了解调用；先用小任务验证，再扩大篇幅。
- **本地模型取决于设备与模型能力**：不需要购买某个指定云服务，但复杂规划、结构化输出和生成速度可能存在差异。

| 本地模型请求 | 发送到你配置的本地服务地址 |
| JSON 备份、正文导出 | 下载到你选择的位置；正文导出不能替代完整备份 |
| 本地记忆工作区 | 用户授权的文件夹；按界面手动核对和确认读写 |
| 可选 GitHub Gist 备份 | 完整项目 JSON 上传至自己的私密 Gist；它不是端到端加密存储 |

**第一次创作后就做一次 JSON 备份。** 在长篇工作区打开“数据管理 → 导出 / 导入 → 导出 JSON”。换电脑、换域名、切换本地端口或清理浏览器数据前，先确认备份已保存；应用自动保存不等于跨设备同步。

本地文件夹的配置与恢复见[本地记忆工作区指南](./docs/MEMORY-WORKSPACE-GUIDE.md)。涉及漫画等媒资时，应使用对应产品和工作区提供的完整导出方式，不能仅备份正文。

## 常见问题

**我必须会编程才能用吗？**

在线版可以直接打开；本地源码版需要安装 Node.js 并运行几条命令。创作主要在界面中进行。旧视频的菜单可能与新版不同，请对照本页“第一次创作”。

**为什么下载 Release 后没有这里的新功能？**

Release 对应发布当时的固定代码。本文描述当前主干，使用最新源码才能取得后续更新；运行中的版本号也包含提交标识，反馈时可以一起提供。

**为什么模型连接失败，或测试成功却生成失败？**

检查 API Key、账户额度、Base URL、模型访问权限与上下文限制。跨域问题按设置页提示使用本地代理。连接测试与实际创作任务不同；先读取错误说明，修正配置后再明确继续。

**换浏览器以后为什么作品不见了？**

本地数据属于特定浏览器配置和站点地址，`localhost`、`127.0.0.1` 与不同端口也不共享数据。回原地址查看，并通过完整备份迁移。

**能不能只写小说，不碰世界引擎或游戏？**

可以。长篇、短篇和两种改编产品独立成立。世界与互动路线是可选能力。

**AI 会自动覆盖我的正文或设定吗？**

正式创作流程先产生候选，由作者编辑、采纳或拒绝；涉及来源变化的旧候选会接受过期检查。重要调整前仍建议保存完整备份。

**可不可以拿去商用？**

仓库代码使用 MIT 许可；模型服务、第三方素材、原作授权与生成内容另按各自条款处理。代码开源许可不代替原作与素材授权。

## 给开发者

StoryForge 使用 React、TypeScript、Vite、Zustand、TipTap 与 Dexie / IndexedDB。正式 AI 任务由 Agent Skill、运行契约与 durable Harness 管理上下文、候选、恢复和采纳。

| 工程入口 | 职责 |
|---|---|
| `CONTEXT_SOURCES` + `assembleContext()` | AI 从哪些登记来源读取内容 |
| `FIELD_REGISTRY` + `AdoptionSchema` + `adopt()` | 候选如何校验并进入正式作品 |
| `PROJECT_TABLES` | 数据的导出、导入、删除、作用域与生命周期 |

世界只保存可版本化的语义内容。跑团、聊天和游戏引用冻结版本，分别拥有自己的媒资、发布与运行数据；共享世界不会被一次游戏自动改写。

```bash
npm run ci       # 注册表、架构、文档、类型、覆盖率与生产构建
npm run ci:e2e   # 隔离快照中的浏览器用户路径
```

单独构建并预览：

```bash
npm run build
npm run preview
```

欢迎改进产品体验、模型兼容性、回归测试、文档、翻译和示例作品。贡献前阅读 [AGENTS.md](./AGENTS.md)、[贡献指南](./CONTRIBUTING.md)和[协作流程](./docs/COLLAB-WORKFLOW.md)；在独立分支工作，通过 PR 交付。
