# 2026年8月17日更新：可编辑记忆工程与本地项目工作区完成
::: warning 历史资料
本页从原 WPS 知识库迁移，用于保留历史记录。内容可能对应旧版本，不应单独作为当前功能状态依据；当前能力请优先查看“开始使用”“功能指南”和仓库最新 Changelog。
:::



这次更新把 StoryForge 的“长期记忆”从浏览器里的零散数据和按需检索，升级为一套由作者、AI Harness、浏览器 IndexedDB 与本地硬盘共同维护的创作状态。

它的重点不是再做一个看不见的“记忆库”，而是让已经确定的作品内容、AI 过程成果和作者决定能够长期保存、外部查看、人工核对，并在安全边界内双向修改。代码已经合入主干，应用语义版本暂时仍为 3.9.1，正式版本号和 Release tag 将由后续独立发版流程决定。

## 你能直接感受到的变化

- 新建项目时可以直接选择“项目存储位置”。例如把项目放到 D 盘的某个小说文件夹，StoryForge 的可读内容、记忆和恢复证据就保存在这个文件夹内。

- 已有项目可以在“设置 → 项目存储工作区”查看、重新授权、更换或解除存储位置，支持用户选择任意本地硬盘目录。

- 浏览器里的 IndexedDB 与硬盘工作区互为映像，但不会在后台互相覆盖。选择文件夹、打开页面、定时器运行或 AI 完成任务都不会自动写盘。

- 项目内修改内容后，由作者点击检查，系统会列出项目改动和下游影响，确认后才更新硬盘文件。

- 作者在硬盘上修改受支持的文件后，同样由作者点击检查；系统先把变化转换为候选并核对作品范围、原值和影响，再由作者确认写回项目。

- 如果浏览器和硬盘同时修改了同一内容，系统不会擅自选边。冲突、缺失、损坏和额外文件都会单独提示，旧内容会先进入历史或回收目录。

## 现在可以在硬盘查看和编辑什么

- Workspace、World、Work 的项目结构文件；

- 每章正文对应的 Markdown 文件；

- 每个作品的“故事核心”中文 YAML；

- 每个作品的“创作规则”中文 YAML。

这些文件不暴露浏览器内部的数字 ID。外部修改不会直接穿透数据库，而是经过候选、当前值校验、影响计划和作者确认后，才走项目原有的正式写入入口。

其它正式项目数据和 Harness 的运行记录、候选、作者决定、采纳、验证与完成回执会进入可读的恢复胶囊。账本、回执和高风险树状结构目前保持只读，避免外部编辑擦掉来源或破坏历史。本轮没有为了“所有表都能编辑”而过度扩张。

## Harness 成果真正沉淀为记忆

- AI 的生成候选、作者修改、采纳或拒绝、验证结果，以及运行成功、失败或取消都会留下可追溯记录。

- Harness 终态与记忆结算在同一个浏览器数据库事务内完成，避免出现“任务显示完成，但记忆里没有回执”的半状态。

- Fast Guard 和 Deep Audit 已接入正式的可恢复运行流程。它们只在作者点击时运行，每次最多调用一次模型；报告只提出证据和问题，不会自动修改正文或正式设定。

- 正文后来发生变化时，旧报告和历史证据仍会保留，但会明确标记为已过期；重新检查会生成新一代记录，不会覆盖旧历史。

- 后续生成和审校优先读取已经确认的设定、角色认知、人物状态、物品、时间线、依赖和来源证据，而不是把向量相似度当成事实裁判。

## 恢复能力

- 浏览器数据仍在时，可以重新授权原目录，先检查差异再继续同步。

- 浏览器数据丢失时，可以从工作区验证项目身份、文件清单、逐文件校验值和恢复胶囊，再重建正式内容、引用关系和 Harness 历史。

- 同步中断或文件权限失效后，可以重新授权并继续；系统只补未完成步骤，不会重复调用模型或重复采纳。

- 旧浏览器里的完成凭据如果依赖已经变化的本地编号，系统会保留全部历史并标记待复核，不会假装旧凭据仍然有效。

## 隐私和 Token

- 文件扫描、解析、哈希、差异比较、冲突判断、影响计划、同步和恢复全部在本机完成，模型调用为 0，不消耗用户的 AI token。

- 只有作者另行启动 AI 生成、文风学习、Fast Guard 或 Deep Audit 时，才会调用用户自己配置的模型服务并产生 token。

- 发现冲突不会自动启动 AI，也不会自动连续修复或批量改稿。

- 本次更新不包含云同步、多人协作、Git 自动提交或服务端托管。

## 一句话说明

StoryForge 已把原来散落在各创作页面里的 AI 调用，收进统一的 Agent + Harness 执行架构：模型只读登记过的上下文，只生成可编辑候选；系统用有界调用、确定性校验、持久化账本和终态回执管理失败与恢复；作者明确确认后，候选才会进入正式设定或正文。

这次更新解决的是“AI 创作过程如何被可靠地执行和交付”，而不是宣称某个模型从此能够稳定写出完美小说。

## 为什么要重构

过去的生成路径虽然已经具备提示词模板、上下文装配和作者确认，但不同功能仍可能各自维护调用、解析、重试和临时候选。模型一旦不遵守结构、网络状态未知或生成质量不足，系统容易出现三类问题：

1.  不知道失败发生在哪一层，也无法准确恢复。

2.  反复重试会继续消耗用户 API，却可能没有可交付结果。

3.  页面级旁路容易绕开统一上下文、作用域、采纳和数据生命周期。

新的架构把创作自由与工程安全分开处理：作用域、引用、结构、写入权限和费用上限保持严格；文学质量、风格和完整度允许分级，以警告、局部修复和作者编辑处理，而不是为了追求机器满分无限重生成。

## 现在的统一主路径

1.  作者请求

2.  -\> Master Agent / 领域 Skill

3.  -\> Run Contract（目标、权限、版本、预算、完成条件）

4.  -\> CONTEXT_SOURCES + assembleContext()

5.  -\> 一次生成

6.  -\> 免费确定性归一化与验证

7.  -\> 必要时最多一次定向修复

8.  -\> CreativeArtifact（草稿、合法片段、问题、假设、用量）

9.  -\> 作者编辑 / 选择 / 接受警告 / 拒绝

10. -\> FIELD_REGISTRY + AdoptionSchema + adopt()

11. -\> 终态回读、回执与影响处理

贯穿整条路径的 PROJECT_TABLES 继续负责表的作用域、导出、导入、删除、迁移、引用重映射和运行记录生命周期。Agent 与 Harness 没有建立第二套数据库或 AI 旁路。

## 本次交付的核心能力

### Agent 不再等于“会聊天的提示词”

- Master Agent 只负责识别意图、选择已登记 Skill、安排依赖和汇总候选。

- 领域 Skill 冻结读源、写目标、提示词版本、工具 schema、上下文策略和回归证据。

- Tool Registry 使用闭集只读工具；模型不能通过自由工具名扩大权限。

- 有限 fan-out 和有限重规划只在明确策略允许时启用，不能变成无边界 Agent 团队。

### Harness 提供可恢复的运行控制面

- 每次运行都有 Run Contract、事件账本、checkpoint、候选 hash、父子 lineage 和终态回执。

- 页面刷新、浏览器中断或长任务恢复时，从同一 ledger 重建状态，不重复已经结算的调用。

- stale 输入、跨 Work/World、错误候选身份、目标变化和采纳前 CAS 漂移会在正式写入前拒绝。

- 下游影响处理以可验证 DAG 展示阻断、就绪、待确认、需人工处理和完成状态，不自动级联重写整本书。

### 创作可靠性采用“严格安全、分级质量”

统一产物状态为：

- ready：结构、作用域和硬边界通过，可进入作者确认。

- usable-with-warnings：结构可采纳，但存在弱因果、重复、信息倾倒等普通质量问题。

- manual-repair：保留原始草稿或合法片段，需要作者手工调整。

- blocked：越权、错作用域、错误引用、stale 或不确定正式写入等安全问题。

系统不会因为一个软问题丢掉整批输出，也不会把软质量警告伪装成数据安全失败。

### API 花费被明确限制

- economy：一次生成，不自动修复。

- balanced：一次生成；只有确定性定位到可修问题时，最多一次定向修复。

- refine：仍最多 1+1；额外语义评审必须由作者显式触发。

- 相同失败指纹再次出现立即停止；授权、余额、权限、stale 和网络结果未知不会自动重发。

- 每个候选记录模型、用途、token、延迟、修复与停止原因。模型价格未登记时只展示 token，不虚构金额。

### 部分设定也能推动故事，而不是反复复述世界观

NarrativeBrief 把当前任务收束为人物欲望、阻力、代价、必须选择、入口状态、退出变化和下一步压力。资料不足时，模型可以在同一次生成中提出显式临时假设；这些假设随候选存在，不会静默升级为 Canon。

上下文优先级也从“谁的资料最多谁占注意力”改为：作者本轮要求、叙事任务、直接前文和当前状态优先，相关 Canon 次之，世界背景和其它参考只在确实影响行动与结果时进入。

### 核心创作入口统一登记

故事核心、故事线、世界观字段、角色创建/补充/关系、灵感反推、角色驱动、卷章纲、细纲、正文、章后记忆与提取、地点、物品、年表、伏笔、历史、参考分析、文风学习等路径已经迁移到 durable Run，或作为明确的只读/内存草稿/模拟运行时入口登记审计。AI 入口检查会阻止新的页面级直连悄悄出现。

## 对作者意味着什么

完成这次更新后，理想交互不再是“点击生成，然后祈祷一次成功”，而是：

1.  系统明确本轮要生成什么、会读取什么、最多调用几次。

2.  生成结果无论完美与否，都尽量留下可编辑内容和准确问题说明。

3.  作者能修改候选、接受普通警告、只采纳合法部分或直接拒绝。

4.  正式数据只有在作者确认后改变；运行中断后可以继续，不必重新付费生成上游。

5.  后续事实、摘要、检索、章纲和年表影响有可见计划，不会悄悄改稿。

## 1. 设计理念

故事熔炉是一个**帮你管理创作全流程的工坊**。

我们认为，写好一部长篇小说，最难的不是码字本身，而是：

- 世界观越写越乱，前后矛盾

- 角色写到后面就"面目模糊"

- 伏笔埋了忘收，时间线搞混

- AI 生成的文字千篇一律，没有个人风格

- 几十万字的项目数据散落各处，换个浏览器就没了

故事熔炉的设计原则：

- **全链路覆盖** —— 从"脑子里有个想法"到"导出完整小说"，不需要在多个工具之间跳转

- **AI 是助手不是主人** —— 每一步都可以手写，AI 只在你需要时介入，且你可以编辑所有 AI 提示词

- **数据永远在你手里** —— 纯前端运行，所有数据存在你自己的浏览器里，不经过任何服务器

- **模块之间互相"知道"** —— 写章节时，AI 能看到你的世界观、角色、伏笔、情感节拍、参考作品分析——不是各管各的孤岛

## 7. 伏笔追踪系统

|               |                              |                                   |
|---------------|------------------------------|-----------------------------------|
| 类型          | 说明                         | 示例                              |

**写章节时，AI 会看到所有未回收的伏笔。** 这意味着 AI 在写作时会自然地呼应已埋设的伏笔，而不会无视它们。

## 8. 状态表与情感节拍

### 8.1 状态表

追踪小说中所有实体的"当前状态"——随着剧情推进，状态会变化。

**五类追踪对象**：角色、地点、物品、势力、事件

**工作流**：

1.  写完一章 → 系统自动调用 AI 分析文本

2.  AI 检测到状态变化（如"主角从练气期突破到筑基期"）

3.  弹出确认窗口，显示变化对比（旧值 → 新值）

4.  你确认后，状态表自动更新

下次 AI 写作时，它会看到最新的状态表，确保不会写出"已经突破筑基的主角还在练气期挣扎"这种矛盾。

### 8.2 情感节拍卡

为每一章规划情绪起伏：

- **节拍标签** —— 如"初遇""误会""和解"

- **场景目标** —— 这个节拍要达成什么

- **情绪基调** —— 紧张/轻松/悲伤/热血/温馨……

- **读者感受** —— 你希望读者在这里感受到什么

- **角色成长** —— 角色在这个节拍中的变化

可以手动编辑，也可以让 AI 根据章节大纲自动生成。写作时，情感节拍会注入 AI 上下文，让生成的文字更贴合你设计的情绪节奏。

## 10. 作品学习系统

这是故事熔炉最独特的功能之一——**向大师学习**。

### 10.1 设计思路

写小说最好的老师就是优秀的小说。故事熔炉让你上传你喜欢的作品，AI 从五个维度拆解它的创作方法论，然后你可以把这些方法论注入到自己的创作中。

### 10.2 三层分析架构

**Layer 1 — 五维分块分析**

上传一本小说后，系统会把原文切成多块，逐块调用 AI 分析以下五个维度：

|                  |                                                                           |
|------------------|---------------------------------------------------------------------------|
| 维度             | 分析什么                                                                  |
| **世界观范式**   | 作者是如何搭建/扩展世界观的？"先给规则再立反例"还是"让主角走一遍再解释"？ |
| **角色设计手法** | 角色是怎么立起来的？外貌/台词/动作/内心/反差/偏执？                       |
| **情节节奏规律** | 开局→转折→高潮→钩子的字数分配？爽点/虐点切换频率？                        |
| **伏笔与悬念**   | 埋了哪些伏笔？明线还是暗线？用"揭晓真相"还是"渐进解密"？                  |
| **文笔与语言**   | 句子长度偏好、描写/对话占比、常用修辞、可模仿的金句模板                   |

分析深度可选：**快速**（大块粗览）/ **标准**（适中）/ **深度**（细块精析）

**Layer 2 — 风格量化 + 章节节奏**

- **风格量化画像**（纯本地计算，不消耗 AI）

  - 平均句长 + 句长分布直方图

  - 对话占比（引号字符 / 总字符）

  - 高频词 Top 50（去停用词的 2-4 字词频）

  - 段落密度（每千字多少段）

- **章节节奏时间线**（AI 驱动）

  - 自动切分章节（识别"第X章/回/节"标题）

  - 每章提取 3-8 个关键节奏点

  - 7 种节奏类型：开场/冲突/反转/高潮/章末钩子/伏笔/松弛

  - 可视化时间线，直观看到每章的情绪起伏

**Layer 3 — 跨作品洞察归纳**

当你学习了多本同类作品后，AI 会从它们的分析结果中归纳出**共性的创作方法论**。

比如：

- "猫腻式悬念递进法"

- "爽文开场三板斧"

- "爽虐交替的黄金比例"

每条洞察包含：标题、详细说明、3-5 条可操作要点、适用流派、来源作品。

# 2026年6月29日更新 · 🎯 长期一致性引擎上线

写长篇最头疼的"写到后面忘了前面、下一章接不上上一章、人物设定前后矛盾、伏笔埋了不回收",这次从底层做了一套系统来治。它不再依赖"把整本书塞给 AI"(写到几十万字根本塞不下),而是给你的作品配了一个不会忘事的资料员,在你每次生成时把相关的前情精准递到 AI 眼前。

具体你能感受到的:

- 🧠 续写交接 — 每写完一章,系统自动记下"这一章结束时:人物在哪、状态如何、有哪些没了结的事、刚定下的新设定";写下一章时自动带给 AI,接得更顺,不再断片。

- 🔍 远距前文召回 — 写到第几百章时,自动从很早以前的章节里翻出相关段落,专治"几百章前埋的伏笔/细节被忘了"。

- 🛡️ 一致性审计 — 写完一章可一键检查,AI 拿你的正文对照上面那套事实+前文,逐条指出矛盾并给出原文证据(只提示,不擅自改你的稿)。

- 🧩 老用户无缝衔接 — 你以前的"角色状态卡"会自动转成事实候选(原数据原样保留、不删不改),确认一下就能用上新能力。

# 2026年7月3日更新：启动方式统一调整

Windows 启动器经过多轮适配后，在不同电脑和本地环境下仍可能遇到打不开或反复跳转的问题。后续不再提供 bat、exe 或 Portable 启动包，Release 保留完整源码，统一按照《使用npm指令启动项目》中的步骤启动。这样用户使用的是同一套项目代码，遇到问题也更容易查看提示和定位。

# 2026年7月13日更新：大纲和长篇写作体验升级

大纲章节现在可以直接拖到其他卷，也可以拖到故事块下，移动后顺序会自动整理，正文内容仍然对应原来的章节。

章节页新增全书查找替换，可以只查当前章节，也可以查整本作品；支持逐处替换、本章全部替换或全书替换。全书替换前会先展示命中内容，并保留本次操作的撤销入口，修改长篇作品更安心。

继续生成卷纲、章纲或单章内容时，系统会参考已经写好的正文和章节进度，尽量接着已有内容往下发展，不会轻易重排或否定已经写好的情节。生成前还可以先查看本次会参考哪些内容。

角色档案补充了更完整的人物信息，已有内容在输入过程中不容易被旧数据覆盖；角色关系编辑在中文输入法下更稳定，新增、修改和删除后都有明确的保存反馈。AI 从正文中提取出的角色关系，采纳后也会同步补充到双方角色档案的人物关系栏。

物品栏和状态卡对角色持有物品的提示更清楚，物品流水可以直接修改，后续写作和审校会参考角色截至当前章节实际持有的物品，减少同一件道具被重复获得的情况。

新增美团 LongCat 模型配置，并完善本地模型和其他兼容服务的使用提示；模型列表可以直接刷新，连接失败时仍可手动填写模型名称。

世界观生成时会更明确地区分世界来源、力量体系、神明与信仰等内容，减少不同设定互相改写；地图生成也会优先使用用户已经填写的世界、地点、山川和势力信息。

JSON 备份导入补齐了细纲角色、场景角色、伏笔和创作规则等内容。导入到新项目后会自动建立新的对应关系，不会把原项目的旧编号带进来。

# 2026年7月15日更新：输入、上下文和正文编辑继续优化

长文本输入框达到高度上限后会在框内滚动，页面不会跟着输入框一起乱跳。AI 上下文设置增加了自动保存状态、格式检查、恢复默认和预设说明，填写错误时不会把之前保存的内容悄悄清掉。

工作流中，如果用户手动修改了某一步的结果，后面的步骤会继续使用修改后的内容。大纲生成前会显示本次实际参考到的故事核心、已有卷纲和其他资料，缺少内容时也会明确说明。

导入文档的操作提示和恢复流程重新整理，长文档解析、粘贴文本和中途取消都更清楚；本地诊断信息下载只包含版本、浏览器和脱敏错误位置，方便排查问题，不会带走作品内容、API Key 或个人存储数据。

本轮也继续修复了若干影响使用稳定性的问题，包括导出正文选错记录、章节上下文取错、旧数据导入后工作区卡住，以及场景拆分采纳后无法打开等情况。已有项目可以直接继续使用。
