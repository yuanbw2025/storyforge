# StoryForge 文字游戏共享架构与复用裁决

> 状态：`DESIGN READY`
>
> 适用范围：`STORYGAME-1`、`CHATGAME-2`、`TEXTADV-1`、`AVG-1`、`TEXTSIM-1`、`TEXTWORLD-1`
>
> 最后裁决：2026-08-13

## 1. 最终决定

**从第一个文字游戏开始考虑复用，但只共享已经稳定、跨类型语义一致的底座；不同玩法以独立能力模块
组合，不先各做一套，也不预造一个包含所有玩法的“万能游戏状态”。**

原因很直接：

- 如果六种游戏先各自实现，分支、存档、回放、发布、AI 权限和数据生命周期一定会出现多套权威，后期
  合并既危险又容易丢存档。
- 如果现在一次抽象全部玩法，尚未经过第二个真实产品验证的概念会被过早固定，最终形成到处都是可选字段、
  产品互相牵连的巨型系统。
- StoryForge 已有 WorldRelease、Narrative、SIM、TTRPG、CHATGAME-1 和 Agent Harness；正确做法是收口这些
  已有事实源，并让每种游戏只增加自己真正拥有的能力。

因此采用三条规则：

1. **稳定底座立即共享。** 世界版本、游戏发布、运行实例、事件、检查点、确定性随机、叙事分支和 Harness
   实例调用不能复制。
2. **玩法模块按需建设。** 关系、背包、技能、组织、危机、区域任务和 AVG 演出各有独立边界。
3. **第二使用者规则。** 某个玩法先在首个需要它的产品内实现受控接口；出现第二个真实使用者时，再将其
   提炼成共享模块，并用兼容测试证明没有改变第一个产品。

## 2. 需要澄清的三种“分支”

“分支”确实几乎所有游戏都会使用，但它实际包含三个不同概念，不能混为一个功能：

1. **内容分支**：作者写好的节点、选择、条件、汇流和结局。
2. **运行分支**：玩家在一次游戏中真正做出的选择，以及该选择造成的状态变化。
3. **存档分支**：玩家从某个检查点复制出另一条时间线，尝试不同选择。

三者共享稳定的内容键和事件序号，但各自只有一个权威：

- 内容分支由 Narrative 内容模型负责。
- 运行分支由 SIM 事件和 reducer 负责。
- 存档分支由 SIM checkpoint/fork 负责。

这样 STORYGAME、AVG、文字冒险和开放世界都能复用“分支”，又不会把剧情路线、世界后果和复制存档混成
一套难以维护的逻辑。

## 3. 六种产品如何组合

```text
共享底座
├─ 世界与发布：World / Work / WorldRelease / Canon Snapshot
├─ 游戏产品：GameDefinition / GameRelease
├─ 叙事内核：Module / Node / Beat / Choice / Condition / Effect
├─ 运行时：Session / Event / Checkpoint / Fork / Replay / Seed
├─ AI 接口：Instance-scoped Harness / Context / Proposal / Validation / Receipt
└─ 能力注册：模块版本、依赖、状态、命令、事件、迁移

独立能力模块
├─ character-interaction：记忆、关系、多人对话
├─ adventure：地点、物品、技能、判定、任务
├─ avg-presentation：背景、立绘、CG、音频、演出时间线
├─ narrative-simulation：资源、组织、政策、危机、延迟后果
└─ open-world：区域、交通、持续行动、传播、动态任务导演
```

每种游戏通过一个产品定义选择需要的能力，而不是继承一棵不断膨胀的类型树：

| 产品 | 必选能力 | 可选能力 |
|---|---|---|
| STORYGAME | 叙事内核 | 作者辅助 AI |
| CHATGAME-2 | 叙事内核、角色互动 | 固定选择、任务目标 |
| TEXTADV | 叙事内核、角色互动、冒险 | 自由文字输入、轻量战斗 |
| AVG | 叙事内核、AVG 演出 | 角色互动、AI 媒资生成 |
| TEXTSIM | 叙事内核、模拟 | 冒险、角色互动 |
| TEXTWORLD | 叙事、角色互动、冒险、模拟、开放世界 | AVG 演出 |

这张表表示组合关系，不表示 TEXTWORLD 要复制前五个产品的界面。

## 4. 第一阶段就固定的共享合同

### 4.1 游戏定义与不可变发布

“世界已经发布”不等于“某个游戏已经发布”。首个产品需要建立统一的游戏产品和发布概念：

- 游戏定义说明产品类型、入口内容、启用能力、玩家规则和兼容版本。
- 游戏发布固定某个 WorldRelease、相关内容和能力版本，成为真正可启动的不可变对象。
- 运行实例只绑定正式发布或带明确哈希的草稿；正式存档不得悄悄读取最新编辑稿。
- 后续六种产品都走同一条试玩、校验、发布、启动和归档路径。

建议的技术实体是 `gameDefinitions` 与 `gameReleases`。真正实施时必须先登记 `PROJECT_TABLES`，并补齐
导入、导出、删除、世界复制、引用重映射和升级反例。

已实现的世界投影合同（2026-08-15）进一步固定：生成器只接受已发布 `WorldReleaseManifestV2`，并把
`sourceWorldContentHash`、`sourceMappingVersion` 与便携 `sourceSelectionJson` 记录在 GameDefinition；
GameRelease 再冻结为 `definition.source`。选择合同只保存 NarrativeModule、角色、关系、重要地点、
artifact、世界词条、StoryArc 和 AVG 媒资的 export ID，不保存本地行 ID。互动角色使用带来源世界 hash 的
最小便携身份快照；生成不再重新读取实时 Character 表，因此世界发布后的改名、删除或新增记录都不能改变
从 WorldRelease 读取到的标题、文本、图结构、关系、地点、道具或媒资。

同日补充的 AI 作者链仍遵守这个边界：`worldGameAuthoring` 是唯一新增读取源，主 Agent 的
`outline.world-game` 只生成可编辑候选，不直接写库。作者确认后由 `ADOPTION_EXTENSIONS` 登记的统一
世界游戏落库器验证 contentHash、便携 exportId 和完整内容图，再复用确定性 STORYGAME/TEXTADV/AVG 构建器。
因此“AI 演化剧情”和“无 AI 快速映射”在候选生成处不同，但从 Narrative 物化、GameDefinition、发布、
GameRelease、SIM 事件与试玩开始重新汇合，不形成第二套 Harness、发布或存档。

### 4.2 叙事内核

当前 NarrativeModule/Node 是正确起点，但完整产品还需要两个共享概念：

- **Beat**：一个节点内有序的旁白、对话、动作或系统提示。
- **Choice**：玩家看到的选项、显示条件、不可用原因、目标节点和确定性效果。

条件和效果继续使用白名单 DSL，不执行任意脚本。叙事内核负责：

- 稳定键、顺序、引用和图校验；
- 进入节点、显示内容、列出可选项、提交选择、抵达结局；
- 不可达节点、死路、无效目标、条件错误和结局覆盖检查；
- 运行状态只保存内容键、变量、访问历史和选择历史，不复制作者内容。

叙事内核不负责背包、好感、组织资源或镜头动画。它只能通过已注册的条件读取器和效果处理器访问启用的
能力模块。

### 4.3 命令、事件与检查点

所有产品遵循同一条写入链：

```text
玩家输入 / AI 候选
  → 结构化命令
  → 权限、版本、前置条件和规则校验
  → 追加领域事件
  → reducer 计算新状态
  → UI 渲染结果
```

共享命令外壳至少携带 instance、baseSequence、stateHash、actor、commandId 和 payload。共享结果必须区分
accepted、rejected、stale 和 requires-confirmation。刷新后由 checkpoint + events 重建，不能依赖组件内状态。

事件按模块命名，例如 `narrative.choice.committed`、`inventory.item.gained`，并由唯一注册表声明解析、降级和
reducer。未知事件不能静默略过后继续写入。

### 4.4 能力模块合同

每个能力模块必须声明：

1. 模块 ID、schema 版本和依赖模块。
2. 自己拥有的状态切片，不能直接改写其他模块内部状态。
3. 接受的命令、产生的事件和确定性 reducer。
4. 可供叙事条件读取的有限 selector，以及可接受的有限 effect。
5. 存档迁移、缺失模块、未知版本和卸载行为。
6. 调试投影、测试样例和性能预算。

产品定义只能启用经过注册的模块组合。循环依赖、缺失依赖和不兼容版本必须在发布前失败。

### 4.5 Agent Harness 的实例接口

正式运行时 AI 不再从组件直接拼 prompt 或直接写状态。正在重构的 Harness 完成 Work-scope 基线后，需要
增加 `HARNESS-RUNTIME-1`：

- run 可绑定 simulation instance、baseSequence、stateHash、visibilityHash 和 releaseHash；
- 从 `CONTEXT_SOURCES + assembleContext()` 取得经过角色视角过滤的上下文；
- 只输出声明过的候选命令或叙事表现，不拥有世界写权限；
- 每次结果保留模型、提示版本、输入哈希、验证结果、采用事件和降级原因；
- run 必须在 Work owner 与 Instance owner 之间恰好选择一个，生命周期进入 `PROJECT_TABLES`；
- 结果返回时重新检查时序，过期候选不能采用。

各产品只定义自己的 Skill 和输出 schema，不再各自复制流式请求、重试、取消、审计和采用逻辑。

## 5. 暂时不能共享的内容

以下内容故意保留在产品或能力模块内：

- 玩家主界面、作者工作台和具体操作流程；
- 一局游戏的节奏、胜负、章节、回合和结束条件；
- 关系维度、技能体系、资源公式、组织决策和任务评分公式；
- AI Skill 的具体提示、候选结构和容错策略；
- AVG 的镜头、转场、音轨和媒资预载；
- 开放世界的区域模拟、任务导演和跨区传播。

出现第二个使用者时，也只抽取最小共同语义。例如 TEXTADV 需要“关系值”时，应先验证它与 CHATGAME-2
的关系记忆是否真的一致，再决定共享 selector，不能因为名字相同就合并全部模型。

## 6. 防止不同游戏互相干扰

1. 产品必须显式声明能力清单；未启用模块的命令和事件一律拒绝。
2. 基础运行时不知道各产品 UI，也不引用产品组件。
3. 模块通过命令、事件和 selector 协作，不直接跨模块改对象。
4. 每个产品有自己的 E2E 样例和发布夹具；共享底座修改要同时回归所有已交付产品。
5. 新 schema 不向所有旧存档强塞空字段；按模块版本迁移。
6. 可选能力失败时不得破坏核心存档；AI、音频和图片均可有明确降级。
7. 一项能力只有一个权威入口；新入口替代旧入口时同步下线旧入口。

## 7. 提炼时机

每项能力按以下过程演进：

1. 第一个产品提出完整需求与边界。
2. 在所属领域内实现接口和测试，不把实现写死在页面中。
3. 第二个产品提出真实差异样例。
4. 只抽取两个产品真正共有的合同，保留各自策略。
5. 运行双产品兼容、旧存档回放和发布往返测试。
6. 抽取完成后删除旧旁路，登记唯一权威。

这一策略既从现在就保护复用，也避免根据想象设计未来五年的万能抽象。

## 8. 跨类型施工顺序

```text
STORYGAME-1
  建立产品发布、叙事 Beat/Choice、通用播放器和分支闭环
    ↓
CHATGAME-2
  建立角色互动模块，并完成 Instance-scoped Harness
    ↓
TEXTADV-1
  建立地点、物品、能力、判定和任务模块
    ↓
TEXTSIM-1
  建立资源、组织、政策、危机和长局模拟模块
    ↓
TEXTWORLD-1
  组合成熟能力，新增区域、持续行动、传播和任务导演

独立表现线：STORYGAME-1 → AVG-1
```

AVG-1 可以与玩法线并行排期，但第一版必须建立在已稳定的 STORYGAME 内容和播放器合同上。

## 9. 共享底座的完成定义

- 任意产品都能经统一发布链生成不可变 GameRelease 并启动实例。
- 同一发布、种子和事件流在刷新、导入后得到相同状态与可选项。
- 内容分支、运行选择和存档分支各自只有一个权威实现。
- 未启用模块、未知事件、过期 AI 结果和非法效果均被明确拒绝。
- 模块升级不改变已有产品的历史回放；不兼容时阻止继续写入并给出恢复路径。
- 新表、新 AI 读写和实例 run 分别进入 `PROJECT_TABLES`、`CONTEXT_SOURCES`、`FIELD_REGISTRY` / Adoption
  治理，不存在组件旁路。
- 至少通过 STORYGAME 与第二种产品的交叉回归，才可宣布“共享模块”真正成立。
