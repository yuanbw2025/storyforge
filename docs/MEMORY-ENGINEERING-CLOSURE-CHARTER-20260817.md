# StoryForge 记忆工程收口纲领

> 状态：当前收口工作的唯一纲领入口
>
> 基线：`MEMORY-0～10` 已由 PR #66 合入主干；本文不推翻既有完成事实，也不重开一套记忆工程。
>
> 目的：在不过度扩张的前提下，补齐“重要 AI 审计统一进入 Harness 记忆结算、作者真正需要的
> 语义内容可在硬盘维护、真实长篇作品证明闭环可用”三个边界。

## 一、结论

StoryForge 已经具备可用的记忆工程主体：作者手动触发三方核对，IndexedDB 与硬盘双向影响，
Harness 终态原子结算，结构化长期一致性优先于 embedding，扫描、同步和恢复不调用模型。

本轮不是扩大成“所有数据都能编辑”的第二套数据库，也不是把每次检查都升级为 AI 工作流。
只完成以下三个收口单元：

1. `MEMORY-CLOSE-1`：把作者显式触发的 Fast Guard / Deep Audit 迁入 durable Harness 和统一记忆结算。
2. `MEMORY-CLOSE-2`：按价值和风险选择性扩大硬盘可编辑语义面，不开放账本和回执给任意修改。
3. `MEMORY-CLOSE-3`：用隔离的真实长篇作品完成双向同步、恢复和连续性验收。

三个单元完成后，记忆工程才可以从“工程闭环已建成”升级为“核心目标经真实作品证明”。

## 二、冻结的目标

后续实现必须同时服务于以下目标，不得以局部便利破坏其中任一项：

1. 作者保存的语义内容、正式 Harness 成果和作者决定都能在浏览器数据与硬盘工作区中恢复和追溯。
2. 作者能够用普通编辑器维护适合人工编辑的内容；硬盘修改只能形成受治理候选，不能直接绕过采纳。
3. 任一方向发生变化后，都由作者主动点击检查；页面进入、定时器和模型完成不得自动覆盖另一侧。
4. 同步必须比较共同基线、当前 IndexedDB 和当前文件，并在写入前显示冲突、作用域和下游影响。
5. Harness 的上下文、候选、作者决定、采纳、验证和终态回执形成连续证据链，后续任务能引用已确认成果。
6. 长期一致性以 Canon、状态、时间、认知、物品、依赖和来源为权威；模型只提出可复核候选。
7. 本地检查、哈希、解析、差异、影响图、同步和恢复保持零模型调用；语义深审只在作者明确触发后计费。
8. 作者最终感知的是可恢复、可解释的创作连续性，不是数据库表、向量库或内部事件数量。

## 三、当前基线与真实缺口

### 3.1 已完成并保持不变

- `projects`、`worlds`、`works`、`chapters` 已登记稳定文件投影和反向采纳。
- 所有可导出正式表与 Harness 证据均进入注册表派生的只读恢复胶囊。
- 文件扫描只读；DB→文件、文件→候选、冲突选边、章节删除和恢复都需要作者显式确认。
- 新 Harness Run 的 `completed`、`failed`、`cancelled` 与 `memory.settlement.recorded` 在同一事务提交。
- `consistencyDossier` 已把结构化事实、认知、状态、物品、时间线和可回链关键词证据送入生成上下文。
- embedding 不是权威来源，删除或关闭后不影响结构化一致性主路径。

### 3.2 本轮只处理的缺口

1. 章节审校页的显式 Fast Guard / Deep Audit 目前直接调用模型并写入兼容 `agentEvents`，没有作为
   独立 durable Run 进入原子记忆结算。
2. 当前直接可编辑文件只覆盖四个根/正文表；若作者在外部维护故事核心、创作规则、人物等高价值
   语义内容，仍只能编辑恢复胶囊之外的其它导出形式，不能走工作区三方核对。
3. 自动化测试证明了协议正确，但还没有用一部长篇真实作品证明长期编辑、冲突、恢复和继续生成的
   用户体验足够稳定。

这些缺口不意味着 MEMORY-0～10 失败，也不授权重构无关模块。

## 四、硬盘内容的三层治理

| 层级 | 内容 | 磁盘策略 | 反向影响 IndexedDB 的方式 |
|---|---|---|---|
| 作者语义内容 | 正文、故事核心、创作规则、人物、故事线等适合人工理解的内容 | 可读；通过登记后可编辑 | 三方核对 → 字段候选 → 影响计划 → 作者确认 → `adopt()` |
| 过程与审计证据 | Harness 事件、候选原文、确认决定、ContextManifest、采纳与结算回执 | 可读、可恢复、不可直接改写 | 只允许由原流程追加；外部修改必须隔离并报告 |
| 派生与本机数据 | embedding、检索 chunk、统计、UI 缓存、文件句柄、临时事务 | 不要求语义镜像 | 从正式来源重建，或只留在本机 |

“所有确定内容同时存在于硬盘”通过作者文档或恢复胶囊满足；“所有表都可任意编辑”不是目标。
如果一个文件的修改不能明确表达作者意图、不能稳定映射到采纳字段，或会破坏不可变证据，它就不得
开放反向写入。

## 五、MEMORY-CLOSE-1：Deep Audit durable Harness 收口

### 5.1 目标

作者在章节审校页显式运行 Fast Guard 或 Deep Audit 时，创建正式 RunContract，冻结章节边界、上下文源、
模型预算和验收标准；报告作为候选进入 durable ledger，终态统一签发记忆结算事件。

### 5.2 必须保持的行为

- 自动章后检查仍是零模型的确定性步骤，不因本任务增加调用。
- 显式 Fast / Deep 每次最多一次模型调用；失败或未知结果不自动重试。
- Deep Audit 继续覆盖因果、动机、伏笔、角色认知、存亡、物品与时序证据。
- 报告只能指出问题和形成修复候选，不能自动改正文、Canon 或下游章节。
- 正文 hash 变化后旧报告保留但标记 stale；重跑形成新代际，不覆盖历史证据。
- 用户能看到上下文范围、调用次数、Token 预算、报告状态和是否已同步到硬盘。

### 5.3 实现边界

- 复用现有 Agent Run event store、ContextManifest、预算追踪、终态验证和记忆结算，不新建审校账本。
- `consistencyDossier`、章节正文和现有 Deep sources 必须通过 `CONTEXT_SOURCES` 装配，组件不得手拼上下文。
- 报告为 candidate/evidence；若后续提供“一键按报告修复”，必须建立新的作者确认写入 Run，不能在审计
  Run 中顺带改稿。
- 兼容读取旧 `agentEvents` 报告；新报告的唯一权威改为 durable Run。兼容投影只能由新 ledger 派生。

### 5.4 完成门

1. success、failed、cancelled、stale、解析失败和预算不足均有反例测试。
2. 新报告能从 Run 追到 ContextManifest、模型证据、候选 hash、作者决定、终态回执和记忆结算。
3. 结算失败时 Run 终态整体回滚，不出现完成但无记忆回执的半状态。
4. 同一正文、同一模式的重复点击不会制造并发重复 Run；显式重跑保留可区分代际。
5. 浏览器刷新和硬盘恢复后报告、状态、引用与 Token 证据一致。

## 六、MEMORY-CLOSE-2：选择性扩大可编辑语义面

### 6.1 准入门槛

每一张候选表必须单独回答并验证：

1. 作者是否能在不了解内部 schema 的情况下理解文件？
2. 外部修改是否能稳定映射到 `FIELD_REGISTRY` / `AdoptionSchema`？
3. 是否具备不依赖数值主键的 documentId / exportId 和明确 World / Work owner？
4. 改名、移动、删除、拆分和合并是否有无歧义语义？
5. 是否能生成确定的下游影响计划，而不是自动批量改稿？
6. 是否能在扫描后再次变化时用 CAS 安全停止？
7. 是否能进入 `PROJECT_TABLES` 的导出、导入、删除、迁移和引用重映射生命周期？
8. 是否有 DB→文件→解析、文件→候选→采纳以及冲突/损坏/越权反例测试？

缺任一项时维持只读 evidence，不为追求覆盖率降低安全门。

### 6.2 候选优先级

以下只是评估顺序，不代表整组自动获准：

1. **首批低歧义试点**：`storyCores`、`creativeRules`。内容紧凑、作者意图清晰，适合先证明通用 codec、
   字段候选和影响计划能否复用；试点通过不代表世界设定覆盖已经完整。
2. **第二批高价值语义内容**：`worldviews`、`worldRulesProfiles`、`characters`、`storyArcs`、
   `foreshadows`。它们直接影响长期创作，但必须逐表解决稳定身份、World/Work 归属、集合增删和引用影响。
3. **后置高风险结构**：`powerSystems`、`cultivationSystems`、`geographies`、`worldNodes`、
   `importantLocations`、`outlineNodes`。只有 DAG/树父子关系、规范章序、章节引用、移动与删除生命周期
   全部通过反例后才开放。
4. **账本型状态**：`temporalFacts`、`knowledgeLedger`、`stateCards`、`itemLedger`、
   `storyTimelineEvents` 默认不允许直接重写历史行。若开放外部维护，文件修改必须形成“纠正/新增/取代”
   候选，经现有账本动作追加或 supersede，不能擦除来源。

### 6.3 文件与交互原则

- 一个文件表达一个作者可理解的语义单元，不把内部表整表倾倒成巨大 YAML。
- 文件只暴露稳定业务字段；内部 ID、hash、receipt、索引和迁移字段由系统维护。
- 自检摘要继续只显示“项目改动、本地改动、双方冲突、缺失、异常、下游影响”。
- 不另建复杂“记忆中心”；现有数据管理入口能承载时优先复用，只有信息无法清楚表达时才增加局部 UI。
- 每次只开放一组投影；注册表、codec、采纳、影响、恢复和测试必须在同一交付单元完成。

### 6.4 完成门

某表只有在主路径、冲突、删除、越权、跨 Work、旧备份、恢复和回读全部通过后，才能从 `evidence`
切换为 `editable`。不得先把文件写出来、以后再补反向治理。

## 七、MEMORY-CLOSE-3：真实长篇作品验收

### 7.1 验收样本

- 一份隔离复制的真实长篇项目，包含已有正文、人物、设定、纲要、状态/物品/时间线和历史 Harness Run。
- 一份多 World / 多 Work 的受控夹具，用于验证作用域和引用隔离。
- 不使用作者当前生产预览项目；验收目录和浏览器数据必须独立，可随时丢弃。

### 7.2 必跑场景

1. 绑定真实目录后检查不写盘，作者确认后才建立首次基线。
2. 项目内修改章节和已开放语义资料，检查影响后写盘并回读 clean。
3. 外部修改同类文件，形成候选和影响计划，确认后写回 IndexedDB。
4. 两侧修改同一内容、删除仍被引用内容、移动/改名和损坏文件时安全停止或明确选边。
5. 完成一次 Deep Audit，验证 Run、报告、结算、硬盘索引和 stale 生命周期可串联。
6. 在同步不同阶段中断、撤销文件授权并刷新，恢复后不重复模型调用、采纳或覆盖历史。
7. 清空隔离浏览器数据库，从目录恢复全部正式内容、Harness 证据和引用；记录数与 canonical hash 可解释。
8. 恢复后继续生成下一章，确认上下文读取到当前 Canon/状态而非过期或跨 Work 资料。

### 7.3 验收判据

- 无不可解释的记录丢失、重复、引用漂移、跨 Work 串台或 hash 变化。
- 无用户手势时文件写入为 0；本地检查和恢复模型调用为 0。
- Deep Audit 只产生报告候选，不自动改稿；Token 与调用次数和账本证据一致。
- 冲突没有默认静默选边；任一失败都保留至少一份可恢复内容。
- 作者能仅凭 UI 和工作区文件理解“哪里变了、为什么受影响、下一步该做什么”。
- 发现问题时修复协议或目标表，不针对验收样本硬编码路径、ID 或文本。

真实验收不承诺“作品永远没有叙事矛盾”。它证明的是：系统能带着正确证据继续创作，发现已知类别的
冲突，并把不确定语义交还作者裁决。

## 八、施工顺序与不可越过边界

```text
MEMORY-CLOSE-0  冻结本纲领
  └─ MEMORY-CLOSE-1  Deep Audit durable Harness
       └─ MEMORY-CLOSE-2A  首组语义投影试点
            └─ MEMORY-CLOSE-2B  按单表验收继续扩展或停止
                 └─ MEMORY-CLOSE-3  真实长篇作品验收与发布判断
```

- `CLOSE-1` 完成前，不再宣传“所有重要 AI 审计均进入统一 Harness 结算”。
- `CLOSE-2A` 只证明选择机制和通用路径；不得据此批量把所有 evidence 表切成 editable。
- 每组投影验收后必须允许作出“当前覆盖已足够”的停止决定。
- `CLOSE-3` 暴露的问题优先按数据安全、串台、恢复、隐性调用、用户误解排序；不得借机扩展无关功能。

## 九、Token、成本与自动化红线

- 文件检查、解析、hash、差异、schema、作用域、影响计划、同步、冲突、恢复：模型调用必须为 0。
- 自动章后确定性一致性守卫：模型调用必须为 0。
- 显式 Fast Guard / Deep Audit：作者每次点击最多一次模型调用，并在调用前显示范围和预算。
- 生成式修复：与审计分离，必须再次由作者触发并形成候选；不得因发现冲突自动连续调用模型。
- embedding 不进入同步基线，不具事实裁决权，不得成为恢复依赖。

## 十、工程与发布门

每个交付单元必须先建立“入口 → 读写 → 三注册表 → 生命周期 → 调用方 → 测试”关联闭包，并满足：

1. 定向回归、反例、旧数据兼容和真实文件往返测试通过。
2. `npm run check:architecture`、`npm run check:required-tables`、`npm run check:ai-manual`、
   `npx tsc --noEmit`、`npm run build`、`git diff --check` 通过。
3. 完整交付运行 `npm run ci`；涉及浏览器文件系统运行 `npm run ci:e2e`。
4. 在独立浏览器数据和隔离目录完成真实 UI/API 操作，不修改作者当前预览项目。
5. 新入口替代旧入口时同步下线旧写路径；兼容读取可保留，但不得维持两个权威写入源。
6. `main` 直接部署，因此半成品默认不可见；数据迁移和新投影必须支持安全回滚且不得删除既有目录。

## 十一、停止条件

出现以下任一情况时停止扩大改动，保留证据并重新裁决：

- 无法证明外部文件修改对应唯一作者意图；
- 需要绕过 `FIELD_REGISTRY`、`AdoptionSchema`、`adopt()` 或 `PROJECT_TABLES` 才能落地；
- 冲突解决可能静默丢失任一侧内容；
- 真实项目恢复出现不可解释的记录数、hash、owner 或引用变化；
- Deep Audit 需要自动重试、自动改稿或不可见 Token 才能维持主路径；
- 新 UI、第二套账本或全表 codec 的复杂度明显超过作者可感知价值。

## 十二、最终完成定义

本轮收口完成必须同时满足：

1. 作者显式 Fast / Deep 审计成为正式 durable Run，并进入统一记忆结算和硬盘恢复证据。
2. 至少一组新增高价值作者语义内容通过完整双向投影门；其余表保留有理由的明确分类。
3. 隔离真实长篇作品完成第七节全部主路径，没有数据安全、作用域或隐性调用问题。
4. 文档、用户操作说明、三注册表和架构守卫与实现一致。
5. 项目能够明确回答哪些内容可编辑、哪些只读、哪些可重建，以及每次模型调用为何发生。

满足这些条件后即停止本轮施工。云同步、多人协作、Git transport、全自动语义修复、全表可编辑和新的
向量记忆平台不属于本轮目标。
