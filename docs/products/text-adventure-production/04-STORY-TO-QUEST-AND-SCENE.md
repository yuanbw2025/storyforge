# 04 · 故事到任务脚本与场景正文方案

> 层级：L2 · 版本：1.14.0 · 生效：2026-09-20
> 性质：内容生产与游戏化编译目标契约。

## 1. 生产原则

故事不是任务列表，任务也不是一条按钮。专业链路必须先确定“为什么发生和人物如何变化”，再确定“玩家做什么、规则如何结算”，最后生产“玩家实际读到和选择的内容”。任何一步缺失都不能由编译器用标题、描述或占位模板补齐。

## 2. 故事圣经与角色圣经

`story.bible` 冻结：核心命题、情绪承诺、玩家幻想、中心冲突、关键真相、风险升级、节奏曲线、伏笔与回收、不可改变的来源事实、允许的产品私域补充、结局候选及它们回答的问题。

`cast.bible` 对每名主要人物冻结：稳定 key、来源类型、公开身份、欲望、恐惧、秘密、关系、说话特征、初始知识、逐阶段可获知识、不可知道事实、状态弧、视觉锚点和禁止写法。玩家身份也必须是正式条目，不能把 prompt 指令当作角色描述。

两个工件分别由故事架构师和角色总监负责；任一未通过引用与连续性检查，不能进入任务设计。

## 3. 叙事弧计划

`narrative.arc-plan` 采用“明确主干 + 可汇流分支 + 状态驱动 storylet”，至少定义：

- Act/篇章、每幕目标时长、开端状态、不可逆转折、高潮与收束。
- 事件链和场景卡：场景目标、进入/退出状态、冲突、人物变化、需要播种/回收的信息、空间锚点。
- 分支点：玩家理解、合法选项、代价、立即结果、持久状态、至少两个后续回响和可能汇流条件。
- 结局候选：正式进入条件、行动链含义、角色与世界回响、失败推进是否能抵达。
- 支线与区域事件插槽：它们可改变的资源、关系、信息、路径或结局条件。

叙事弧不能包含未登记运行字段；需要的新语义先提交能力/状态注册提案，经确定性合同批准后才可被任务脚本引用。

一小时旗舰不再要求 provider 在一次长 JSON 中同时稳定输出三幕、12 张场景卡、全部决定和回响。`text-adventure-narrative-designer` 使用唯一核心 Skill `narrative-design.v1` 执行两个顺序 Run Contract：`content.narrative-arc-scenes` 精确覆盖三幕、场景卡和结局槽位，`content.narrative-decision-plan` 只覆盖玩家决定、选项、持久效果和回响场景。两个候选分别严格解析后，`content.narrative-arc-plan` 以零模型调用合并，并再次校验角色、场景、地点、决定、回响与结局引用。任一分步缺失都暂停在其原 owner，不允许装配器补写。

正式叙事弧通过后，独立的 `text-adventure-ending-route-designer` 运行 `ending-route-plan.v1`，产出 `content.ending-route-plan`。它不新增结局或状态，只能从叙事决定已经登记的 `persistentEffectKey` 中为每个结局选择必要条件，并说明这条行动链为何兑现该结局。严格 parser 要求结局不重不漏、同一决定的互斥效果不能同时出现、路线签名不重复，并穷举所有被引用二元决定组合，证明每种组合恰好命中一个结局且每个结局至少可达。不能再由编译器按决定编号或数组前缀臆造结局条件。

## 4. 主线任务设计

`quest.main-plan` 把每幕拆成一个主线任务链，而不是把全篇包成“一条任务、一个阶段、一个目标”。一小时旗舰至少包含：

- 1 条贯穿主线，至少 3 个阶段、8 个正式目标、20 个推进所需行动。
- 每个目标的叙事目的、发生区域/地点/场景、可用行动类别、前置、代价、检查、成功/代价成功/失败推进结果。
- 至少两个目标有两种通用解法；解法可改变资源、关系、知识、物品或后续场景，而非只换一句文案。
- 每个阶段有入口、完成、失败/替代和阶段过渡；不得由无条件移动越过。
- 主线必须声明支线/事件的接入点和可接受回响，给后续岗位使用。

“20 个推进所需行动”按玩家在任一有效主路线中真正能够执行的正式行动计数：该路线所经过场景内完成必要目标的任务行动，加上已由 `adventure-action:*` 桥接且能经过规则校验的叙事选择行动；最终取所有可达路线中的最小值。只存在于另一分支的任务行动不能给当前路线凑数；任务标题、目标记录、未桥接按钮或 Narrative 图上的裸连边也不能充当行动量。

## 5. 支线与区域内容

`quest.side-plan` 的每条支线至少两个阶段或三个目标，有独立人物诉求、与主线主题的映照、可选择代价及可回响结果。`storylet.plan` 定义触发条件、权重/冷却、可重复性、状态影响和过期条件。

支线设计师必须读取主线、角色、系统和空间工件。与主线状态、人物弧或世界理解都无关系的“去某地按一次按钮”视为填充内容，不能计入旗舰体量。

## 6. 任务脚本

`quest.scripts` 是设计与 runtime 之间的版本化中间表示，由任务脚本工程师生成、确定性编译器校验。每个脚本包含：

- quest/stage/objective/action 的稳定 key 与显示文本分离。
- 进入条件、显示条件、可执行条件、资源消耗、种子化检查和四档结果。
- 只使用已登记通用操作的效果：flag/fact、资源、能力成长、关系、物品/装备、任务阶段、位置、时间、storylet 和结局候选。
- 每个效果对应的叙事回响 key；每个叙事分支对应正式状态差异或明确标记为纯表达分支。
- 幂等性、不可重复/冷却、失败推进、软锁保护和替代合法行动。

模型产出只是候选。解析器拒绝未知字段、悬空引用、跨产品状态、未授权专用机制、无界数值、无回响关键选择和无法抵达的任务阶段。

当前实现仍以 `content.quest-script` 为唯一正式任务脚本工件，但不要求 provider 一次输出整场游戏。
`text-adventure-quest-scripter` 的唯一 `quest-script-compile.v1` Skill 把每幕按 `single/multi` 两类目标各执行一个 Run，并另执行补充内容 Run，产出
`content.quest-script.main.act-{1..3}.{single|multi}` 与 `content.quest-script.supplemental`；每个子工件严格解析、单独计费和恢复，随后由确定性装配任务不重不漏合成正式工件。V1 脚本逐项目标和解法冻结
`automatic/check`、已登记能力、难度、代价成功下限、时间成本，以及成功、代价成功和失败推进文本；
支线与区域事件同样逐项精确覆盖。它有意不开放任意 effect 数组：状态效果继续由确定性编译器根据上游计划中的已验证持久 key 生成，避免模型借“脚本”名义写入未登记状态。

冻结系统能力表是唯一合法 `abilityKey` 来源。支线与区域事件岗位在自身候选边界就必须使用精确白名单，任务脚本 parser 再做第二次闭合检查；禁止在下游把自造复合能力静默改名。时间、难度和代价成功下限允许把纯数字字符串或有限小数确定性归一为受合同约束的整数，但不能借归一化改变故事、解法或状态语义。单幕两个 Run 合计按真实模型测量预留 6% 总输出包络，其中多解目标独享 3.5%；区域事件预留 4.5%。不能因把结构工件的预算经验照搬到玩家可见文本而误杀足量内容，也不能为了缩短 JSON 把多个合法解法压成一个。模型若输出冻结清单之外的多余目标或解法，协议层只丢弃超出部分并记录归一化证据；任何应有目标或解法缺失仍然失败，绝不复制其他文本填空。

V1 完成后，主线运行时规则、支线/事件行动种类、检查难度、时间和三档反馈均消费该工件；
缺少条目、使用未知能力、自动结算夹带检查参数、难度区间无效或失败没有前进文本都会在装配前失败。

## 7. 场景与对白生产

分场作者按有界场景包生产 `scene.script.*`，不再一次输出全篇或整幕巨大 JSON。一小时旗舰
把三幕各自确定性拆成两个冻结包：`content.scene-script.act-{1..3}.part-{1|2}`，共六个
Scene Writer Run。六个 Run 使用同一专业岗位与同一 `scene-script.v1` Skill，但各自拥有独立
场景清单、输入哈希、预算、attempt、checkpoint、receipt 和候选工件；它们不是一次模型调用
伪装成六份结果，也不是为了分包再注册六个伪 Skill。

场景槽位、连边、分支槽位和结局槽位由确定性叙事骨架先行生成。Scene Writer 只能填充已分配的
标题、摘要、正文节拍、对白、选择措辞和结局表达，不能新增或改写 key、位置锚点、任务效果、
状态字段和结局规则。解析器逐幕验证：

- Act、场景、选择和结局 key 必须精确覆盖本 Run 的冻结槽位，顺序稳定且无重复。
- 场景标题、模块标题和结局标题必须复用上游已采纳工件，禁止在正文阶段偷偷重写设计事实。
- 对白 speaker 只能引用角色圣经中的稳定 key；非对白节拍不能伪装 speaker。
- 商业档每幕必须达到按目标总量分配的最低主路线文本与对白量；终幕每个结局有独立正文下限。
- 商业档每个结局必须在摘要或正文中逐项兑现故事圣经冻结的全部 `requiredConsequences`，并至少包含一名正式非玩家角色的对白回响；堆足字数但不交代选择后果、只由旁白宣告结果或由玩家自说自话，均拒绝接收。
- 非终幕不得生成结局；终幕必须完整覆盖全部结局，不得留下“待续”或占位文本。

`order` 和空的 `unavailableReason` 属于非叙事语义的显示字段：模型省略顺序时按冻结数组位置补齐，
空的不可用说明统一补为“当前状态不满足此行动条件”。该归一化不得扩展到 key、场景、选择、
正文、speaker、状态或结算字段；这些字段缺失或变化仍必须失败，避免用“容错”掩盖内容缺口。

每幕两个候选全部通过后，`content.scene-script.act-{1..3}` 由三个确定性分幕装配任务生成；
装配器重新验证本幕场景、选择、结局和 beat key 的完整覆盖。三幕分场工件和三幕对白审校
全部通过后，`integration.narrative` 才装配统一的 `content.narrative`。两级装配都只合并已验证
候选并补入冻结节点/连边/空状态容器，不调用模型、不创造正文，也不替作者补齐缺失场景。
任何分包内或跨幕 beat key 冲突、悬空引用或槽位缺失都会在进入 RuntimePackage 前失败。

叙事弧中的 `persistentEffectKey` 和 `echoSceneKeys` 不是供模型自述的备注。编译器把每个选择写成
正式条件，并在登记的回响场景只向持有该条件的路线暴露可回放“决定回响”；多结局只使用已验收
`content.ending-route-plan` 中互斥且完备的效果条件，最终菜单不能覆盖玩家此前的路线。自动游玩必须从每个结局的全部图路线中找到
一条满足任务、物品、状态和决定条件的真实可执行路线；图上有连边但规则上不可执行不算可达。
决定计划的严格解析器只接受位于决定场景之后的回响场景；每个选项至少两个且不得引用当场或历史
场景。商业候选的运行质量门还会反向核对发布包：选择行动必须写入正式持久条件，并且至少两个可达
后续叙事节点存在由该条件门控、拥有玩家可见结果文本的回响行动。只有状态变化、没有运行期可观察
回响的分支不能计入旗舰的关键决定数，直接删掉编译回响的发布包也不得通过推荐门槛。

每个场景包 Run 只读取登记的 `product-production.adventure-scene-script-inputs`：本包精确场景卡、
相关角色、所用地点、对应主线目标/脚本、同地点支线与区域事件、当前决定，以及相邻幕的单一
交接摘要。完整上游工件仍保存在数据库并参与输入哈希，但不会重复塞进模型上下文。投影采用字段
级有界摘要，不裁掉冻结 key、因果、解法或场景槽位；任一场景包仍超过登记预算就正式失败并要求
修改计划，不能在末尾静默截断正文依据。

Scene Writer 的 Skill 继续以 `maxOutputTokens: 24_000` 限制玩家可见 JSON；冻结 Plan 则为六个
同构场景包分别预留 `32_000` billable output tokens，因为 Provider usage receipt 还可能把隐藏
推理计入 output。真实首包回执曾达到 `29_343`，并超过旧 Plan 的 `24_128` 预留；现行预留等于
24k 可见上限加有界 8k 推理余量，按该证据保留 2,657 token 余量。执行计划升级必须改变这六个
task-local reservation，不能只提高被 200k baseline 封顶的 Brief 总输出预算；总实际用量仍由
Build lifetime ledger 和作者授权总预算共同约束。

一小时旗舰的正文预算由 DAG 分配到各幕和场景，并保留 15% 修订空间。正文至少覆盖：开场、每个关键行动的前因与结果、人物对话、分支回响、失败推进和完整结局。重复的地点说明、按钮描述和系统标签不计正文预算。

独立对白编辑在每幕场景完成后分别执行 `content.dialogue-pass.act-1/2/3`：逐条覆盖本幕所有 dialogue beat 与玩家选择，统一人物声音、检查知识越界、补足玩家回应、去除说明书式对白和混合语言残片。每个实际说话角色必须形成声音与知识边界评估；每条对白和选择必须明确 keep 或 revise，不能用抽样审查冒充全量 pass。

该 Artifact 只能提供对白文本以及选择 `text/description` 的替换值，不能改 key、speaker、节点、任务效果、条件、资源或状态。确定性装配器验证覆盖率和不变量后应用修订；漏审、重复、伪造 speaker、keep 却改文案、revise 却没有实际变化都会失败。它有独立 Agent、Skill、Run receipt 和有界修复闭包，不能由 Scene Writer 自审或只靠最终通用质量分数替代。

Scene Writer 或 Quest Scripter 的质量返修不是“重新写一个更短版本”。返修上下文必须冻结并提供上一轮已验收的本任务完整工件，Agent 在完整底稿上逐项处理归属问题，保留未命中的场景、对白、选择、任务解法和正文体量，再输出完整候选。任何只返回被点名片段、把长正文概括成摘要或遗漏同批槽位的结果均由确定性门拒收。

Dialogue Editor 只读取登记的 `product-production.adventure-dialogue-inputs`：角色声音/知识边界、
本幕场景交接状态和本幕完整玩家可见文本。它不读取玩法系统、媒资、数据库表或未冻结世界来源。
一小时夹具已证明全篇单次审校会越过登记预算，因此 V1.5 将三幕固定为三个独立 Run；单幕投影仍
超出预算时才继续升级为更小的显式对白分包计划。

## 8. 连续性整合

连续性编辑读取确定性投影和完整可见文本，检查因果、时间、位置、物品、关系、知识、动机、伏笔、节奏、重复、选择铺垫/结果和结局回收。修复必须定位到工件与字段，由原岗位重做；审查 Agent 不直接偷偷改稿。
