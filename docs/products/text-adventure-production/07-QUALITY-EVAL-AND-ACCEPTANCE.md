# 07 · 质量评测与验收方案

> 层级：L2 · 版本：1.2.0 · 生效：2026-09-08
> 性质：发布质量门目标契约；模型评分只能提供评审意见，不能单独证明通过。

## 1. 证据层级

1. 严格 parser 与引用检查证明协议合法。
2. 确定性图、状态、路线和字量分析证明结构可行。
3. 自动游玩证明可达、可恢复、无软锁和规则一致。
4. 独立 Agent 评审提供因果、人物、节奏和语言问题候选。
5. 人类完整试玩证明真实时长、理解、情绪与交互体验。

低层证据不能代替高层证据；模型输出 `passed: true` 或全部 4 分不能让 Build 通过。

## 2. 路线级确定性指标

对从入口到结局的可达路线进行有界枚举；循环按状态与访问上限处理，并输出无法穷举的理由。每条路线分别计算：

- 玩家实际可见的唯一叙述、对白、选择结果和结局文本单位；配置、标签、标题、隐藏描述和未走分支不计入。
- 正文/对白比例、对白轮次、必需行动数、可选行动数、场景数、任务阶段、资源/关系/物品/flag 变化。
- 分支点、有效决定、汇流距离、持续差异跨度、后续回响和抵达结局。
- 预计阅读时间、决策时间、系统交互时间；预计值明确标记，推荐候选必须再由真人计时校准。
- 重复文本、超长按钮、占位符、prompt 泄漏、混合语言碎片、空结局和无结果选择。

内容体量不得再把地点说明、物品描述、任务标题、动作成功/失败所有变体相加冒充单条主线；`brief.scale.targetPlayMinutes` 只能是目标，不能作为实际时长证据。

## 3. 结构和系统门

- 所有节点、场景、任务、目标和结局可达；无非结局死路、软锁、悬空引用和无法退出循环。
- 每个合法行动都有前置、结算、不可用原因和至少一个可显示结果；关键行动有失败推进。
- 状态机不变量、资源可行性、事件幂等、种子化重放、存档往返和分支隔离通过。
- 主线不能被无条件移动越过；支线/区域内容不能只靠一个完成动作充数。
- 角色知识、位置、物品持有、关系、时间和任务阶段与叙述一致。

## 4. 内容门

独立评审至少检查因果与连续性、玩家能动性、路线差异、节奏、铺垫回收、人物动机/变化、情绪触达、文本清晰度/风格和重复。每个问题必须包含 Artifact key、场景/字段、证据、严重度和责任岗位。

推荐候选除满足 [`01-DELIVERY-CONTRACT.md`](./01-DELIVERY-CONTRACT.md) 的硬下限外，还必须：

- 开场十分钟内明确玩家身份、目标、风险和第一个有意义行动。
- 中段至少一次改变玩家对冲突或人物的理解，并让先前选择产生回响。
- 高潮要求玩家使用此前获得的知识、关系、物品或能力；不能只点击最终选项。
- 每个主要角色有可观察的欲望与变化，不作为纯任务牌或设定讲解器。
- 结局回答核心命题，说明关键行动造成何种结果，同时保留适度文学表达。

## 5. 自动游玩矩阵

必须包含黄金路线、至少一条替代解法、失败推进路线、每个结局、随机策略长回合、资源临界、跳过支线、完成支线、中途刷新、存档/读档/分支、AI 不可用、媒资不可用、损坏恢复、导出导入和删除生命周期。测试夹具必须给出真实内容与预期状态，不能只列名称。

当前 `qa.autoplay` 已确定性执行其中可在内存中忠实证明的八类证据：黄金路线、每结局、替代路线、失败推进、状态 JSON 往返、分支克隆隔离、AI 离线与媒资离线。它实际调用与 runtime 相同的叙事条件/效果、Adventure 前置条件、能力/随机判定、效果和状态 parser；主线 Choice 若尚未解锁，先执行当前地点合法的主线目标行动，不把图可达误当成可点击。

随机长回合、资源临界、支线跳过/完成、真实刷新、存读档/分支、损坏恢复、导入导出和删除生命周期必须在隔离浏览器/IndexedDB E2E 中执行。Playtest Director 生成的 `quality.playtest-plan` 必须不重不漏覆盖 15 类验证、给出操作步骤、预期断言和证据引用；它是测试计划，不是执行回执。

## 6. 人类验收

社区推荐候选至少需要：

- 作者逐层确认 Brief、来源、故事/角色圣经、核心循环、主要角色视觉锚点和最终 Build。
- 一名未参与生产的人从新会话完整通关黄金路线并计时，记录理解障碍、无聊点、错误、选择感受和结局反馈。
- 另一条有效路线或失败推进路线完成抽查；刷新、存档和恢复进行真实浏览器验证。
- 所有 blocking 问题关闭；重要 warning 有明确接受理由；最终 receipt 绑定同一 Build/hash，旧 Build 证据不得复用。

当前实现使用两个互补而不可互相替代的回执。通用 `playthrough.main-route` 只冻结作者确认的 Narrative 起点、逐次 Choice 和结局；文字冒险专属 `text-adventure.playtest.human-coverage` 才负责社区候选的人类覆盖。后者必须同时包含一场作者试玩和一场声明“未参与本 Build 生产”的独立玩家试玩，两场使用不同的新 Preview 会话和不同事件流。试玩者以公开昵称或匿名代号签署身份声明，不能把同一存档改标签重复提交。

每场专属回执从权威 Runtime Event Log 重建并复验：

- 同一 `Build/packageHash/previewHash/briefHash` 下的起点、全部 Choice、结局和 `adventure.action.committed`；Choice 边和 Action key/kind 必须存在于冻结 RuntimePackage。
- 实测时间必须位于目标时长的 75%–125%；目标 60 分钟即 45–75 分钟。
- 叙事选择不少于 `max(2, ceil(targetMinutes/6))`，60 分钟即至少 10 次。
- 不同且实际尝试过的有效行动不少于 `max(6, ceil(targetMinutes/4))`，60 分钟即至少 15 个；重复观察或不可执行命令不能刷满指标。总行动数和交谈行动数仍单独保留。
- 理解、节奏、玩家能动性、情绪触达四项均为 1–5 分且不低于 3 分；理解障碍、无聊点、错误、选择感受和结局反馈必须显式填写，“无”也是有效事实。
- 未关闭 blocking 问题必须逐项记录；存在任一项时该会话失败。

只有一个角色通过时 gate 状态为 `needs-human`；任一角色的最新会话失败时为 `failed`；两个最新角色会话均通过且事件流不同才为 `passed`。新失败证据会使 Build 的可恢复 `release-ready` 投影降回 `preview-ready`。社区包离线验证会重算会话、聚合和 receipt hash，并在候选档案公开两类玩家的实测时长、选择、有效行动、交谈和评分；UI 因此要求试玩者使用可公开的代号并提示文字反馈会进入候选证据。

## 7. 当前 Build #4 的预期判定

新的质量实现必须让《潮钟群岛：最后的灯火》Build #4 至少因主路线可见字量不足、有效对白不足、无正式可交互 NPC、有效决定与持续回响不足、主线任务阶段/目标不足、结局正文不足和缺少当前 Build 真人完整试玩回执而失败。若仍显示 release-ready，视为质量门实现错误。
