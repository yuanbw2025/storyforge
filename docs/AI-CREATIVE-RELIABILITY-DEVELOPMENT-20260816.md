## 1. 文档目的

Agent + Harness 重构已经建立了上下文治理、严格候选、作者确认、受治理采纳、长运行恢复、
终态回读和评测证据，但 H86 证明当前产品仍可能在模型协议失败后重复花费，最终不给作者任何
可编辑产物。本工程不重做 Harness，而是在现有架构上补齐“有限成本内交付可用创作结果”的
产品闭环。

目标不是让随机模型每次达到机器意义上的绝对正确，而是：

> 安全边界必须严格；创作质量允许分级；调用成本必须有界；失败也应尽可能留下可编辑产物；
> 信息不足时仍要推进故事，但新增假设不能静默成为 Canon。

## 2. 最终用户目标

作者只提供一个灵感、部分世界观、少量角色或不完整故事方向时，StoryForge 应当能够：

1. 识别现有正式事实、作者本轮目标和缺失的叙事驱动力。
2. 在不篡改 Canon 的前提下提出可见的临时假设和故事脚手架。
3. 生成故事线、规划、场景和正文候选，并持续推进人物目标、阻力、选择和状态变化。
4. 默认一次生成；必要时最多一次针对明确问题的修复；不隐藏调用，不要求第二个服务商。
5. 严格阻止越界、错作用域、非法写入和错误引用；把普通质量问题作为警告交还作者判断。
6. 即使结构或质量未完全达标，也尽可能交付合法片段、原始草稿和准确的问题清单。
7. 让作者主要进行选择、局部修改和提升，而不是全程监工或从失败页面重新开始。

## 3. 成功定义

### 3.1 工程成功

- 同一产物默认最多一次生成和一次定向修复；不存在隐藏第三次调用。
- 所有调用、token、延迟、失败原因和修复原因均可恢复、可审计。
- 结构失败不会绕过 `FIELD_REGISTRY + AdoptionSchema + adopt()` 写入正式数据。
- 合法片段和原始草稿不会因一个软问题被整批丢弃。
- 刷新、关闭浏览器或中断后恢复同一结果，不重复已结算调用。
- 新能力不建立第二套上下文、写回、数据库、Runner 或模型直连。

### 3.2 产品成功

首个社区体验门至少同时满足：

- 首次或一次修复后取得可编辑产物的比例不低于 80%。
- 完全无产出的比例不高于 10%。
- 每个单产物平均模型调用不高于 1.5 次，最大不高于 2 次。
- 新路径每份被作者接受产物的 token 和估算成本不高于旧路径 1.5 倍。
- 同模型盲评中，新路径“愿意继续编辑”的比例显著高于旧路径，且不存在安全退化。
- 部分设定样例中，正文或规划必须发生事件/目标/关系状态变化，不能只复述世界观。

“替作者完成约 80% 工作”属于真实用户结果假设，不以机器测试自证。只有社区作者的保留率、
修改时间和连续章节数据能够支持该表述。

## 4. 范围与非范围

### 4.1 本工程范围

- 创作结果分级、问题分类、降级产物和可恢复证据。
- 产物级调用上限、质量模式、停止策略和费用透明。
- 免费确定性归一化、精确错误路径和最多一次定向修复。
- 故事线纵向切片。
- `NarrativeBrief`、部分设定叙事脚手架和上下文优先级。
- 故事线到规划、场景、正文的既有链路适配。
- 已有作者偏好、长篇连续性和章后链路的可靠性收口。
- 新冻结评测集、同模型 A/B、长篇验证和社区体验门。

### 4.2 明确非范围

- 不新增“失败处理 Agent”或默认独立 Critic Agent。
- 不要求用户配置第二个服务商或备用模型。
- 不自动接受模型输出或自动写入 Canon。
- 不自动级联重写整本书。
- 不改文字游戏分支、世界发布出口或社区后端。
- 不用 H85/H86 已消耗 held-out 继续调参。
- 不把文学主观质量变成绝对硬门。

## 5. 架构归属

本工程是现有 Harness 的横向能力，不是新的顶层体系。

```text
作者请求
  -> 现有 Master Agent / 专业 Skill
  -> CONTEXT_SOURCES + assembleContext()
  -> 产物级 CreativeReliabilityPolicy
  -> 一次生成
  -> 免费确定性归一化与验证
  -> 必要时一次定向修复
  -> CreativeArtifact（结果、问题、假设、用量）
  -> 作者编辑/选择/接受警告/拒绝
  -> FIELD_REGISTRY + AdoptionSchema + adopt()
  -> 现有 terminal verifier / receipt
```

职责边界：

| 层 | 新增职责 | 禁止事项 |
|---|---|---|
| Harness | 产物级预算、调用停止、失败证据、恢复 | 代替领域 Agent 创作 |
| Skill/领域节点 | 输出结构、叙事任务、可修复问题映射 | 自建调用循环或写库 |
| 确定性代码 | 解析、归一化、引用/作用域/硬边界、问题定位 | 猜测缺失创作语义 |
| 模型修复 | 只修已定位问题，保留其它内容 | 无错误范围的整体重写 |
| UI | 展示状态、问题、假设、调用与作者动作 | 把警告伪装成通过或失败 |
| Adoption | 只采纳最终合法、作者确认内容 | 采纳原始降级文本 |

## 6. 三注册表与数据生命周期判断

### 6.1 读取

- 基础可靠性合同只处理已经组装的输入和模型输出，不新增 Context Source。
- `NarrativeBrief` 优先作为当前 Run 的派生输入；只有当独立读取方需要从正式项目读取时，
  才登记新的 `CONTEXT_SOURCES` 项。
- 正式事实继续只从现有 `storyCore`、`storyArcs`、`activeNarrativeBlueprint`、
  `characterDrivenPlan`、`detailedOutline`、章节正文、连续性交接、摘要、检索和 Canon 来源读取。

### 6.2 写入

- 创作可靠性状态、问题、假设、调用证据优先保存在现有 Agent candidate payload / Run ledger，
  不属于 Canon，不新增 `FIELD_REGISTRY` 写目标。
- 故事线、章纲、细纲、正文、作者偏好等正式写入继续使用已有 field key、AdoptionSchema 和 `adopt()`。
- 若后续需要把作者确认的临时假设固化为正式世界/故事字段，必须按对应既有字段逐项采纳，
  不允许把整个 `NarrativeBrief` 直接写成正式设定。

### 6.3 表与生命周期

- 第一阶段复用 `agentRuns / agentRunEvents / agentRunCheckpoints / agentEvents`，不新增表或迁移。
- candidate payload 扩展必须保持旧事件兼容，并进入 candidate hash、stale、导入取消和作用域校验。
- 若实际施工证明现有 ledger 无法承载可查询问题历史，必须先暂停并另写 schema/迁移设计；
  不允许组件临时写 localStorage 形成第二事实源。

## 7. 核心数据合同

### 7.1 结果状态

```ts
type CreativeArtifactStatus =
  | 'ready'
  | 'usable-with-warnings'
  | 'manual-repair'
  | 'blocked'
```

- `ready`：结构、作用域和硬边界通过，可直接进入作者确认。
- `usable-with-warnings`：可采纳结构合法，但存在非阻断质量问题。
- `manual-repair`：保留了可编辑原始草稿或合法片段，尚不能直接采纳。
- `blocked`：存在越权、错作用域、错误引用、无法确定目标或其它数据安全风险。

### 7.2 问题合同

```ts
interface CreativeArtifactIssueV1 {
  version: 1
  code: string
  severity: 'info' | 'warning' | 'error'
  disposition: 'advisory' | 'repairable' | 'blocking'
  path: string
  message: string
  suggestedAction: 'none' | 'edit' | 'repair-once' | 'remove' | 'replan'
  evidenceRefs: string[]
  deterministic: boolean
}
```

硬阻断仅覆盖：

- 项目、World、Work 或记录作用域错误。
- 未登记读取/写入、非法字段、非法 FK 或不存在 ID。
- 会导致不确定正式写入的结构错误。
- 未来信息、角色私人认知或作者明确禁写边界的确定性违反。
- stale 输入或候选身份/hash 不匹配。

其余创作问题默认是提醒或可修复问题，例如弱因果、事实覆盖不足、重复、信息倾倒、没有推进、
风格偏离、可选字段缺失。

### 7.3 创作产物合同

```ts
interface CreativeArtifactV1 {
  version: 1
  policyVersion: string
  status: CreativeArtifactStatus
  qualityMode: 'economy' | 'balanced' | 'refine'
  originalText: string
  editableText: string
  validFragments: CreativeArtifactFragmentV1[]
  rejectedFragments: CreativeArtifactFragmentV1[]
  issues: CreativeArtifactIssueV1[]
  assumptions: CreativeAssumptionV1[]
  canonEvidenceRefs: string[]
  callEvidence: CreativeCallEvidenceV1[]
  repair: null | CreativeRepairEvidenceV1
}
```

合同必须进入 candidate hash；解析时严格校验版本、状态、问题闭集和调用单调性。旧候选没有该字段时
继续按历史语义读取，不伪造问题或用量。

### 7.4 临时假设

```ts
interface CreativeAssumptionV1 {
  id: string
  text: string
  derivedFrom: string[]
  confidence: 'low' | 'medium' | 'high'
  conflictsWith: string[]
  status: 'provisional' | 'author-confirmed' | 'rejected'
}
```

默认只允许 `provisional`。作者确认后也必须映射到明确的既有正式字段，不能仅修改该状态就冒充 Canon。

### 7.5 叙事驱动力

```ts
interface NarrativeBriefV1 {
  version: 1
  creativeGoal: string
  protagonistDesire: string
  obstacle: string
  stakes: string
  requiredChoice: string
  entryState: string
  exitChange: string
  nextPressure: string
  mustHonor: string[]
  mustNotReveal: string[]
  creativeFreedom: string[]
  assumptions: CreativeAssumptionV1[]
}
```

`NarrativeBrief` 是本次创作的运行时合同。它优先于背景资料，但不能覆盖作者明确要求或 Canon。

## 8. 调用与费用政策

### 8.1 质量模式

| 模式 | 默认调用 | 自动修复 | 语义评审 |
|---|---:|---:|---:|
| `economy` 节省 | 1 | 0 | 0 |
| `balanced` 均衡 | 1 | 仅确定性确认可修时最多 1 | 0 |
| `refine` 精修 | 1 | 最多 1 | 评审必须由作者显式触发 |

### 8.2 强制停止规则

- 单产物物理模型调用最大值为 2。
- 相同失败指纹再次出现立即停止。
- 非重试型 4xx、授权、余额、模型权限和 stale 错误不自动重试。
- 网络结果未知时不自动重发；先恢复服务商/ledger 证据。
- 预算耗尽交付当前产物，不把“没有达到满分”转化为更多调用。
- 多产物计划必须在开始前显示产物数、总调用上限和预计 token；作者可取消未开始步骤。

现有团队 `maxCalls=7` 只保留为旧 Run 兼容上限；新 Run 还必须冻结产物级政策，不能用团队上限
解释同一个产物的第三次调用。

## 9. 确定性归一化与一次修复

允许免费归一化的操作必须语义无损并有反例测试：

- 去除包裹整个响应的单一 Markdown JSON 围栏。
- 从纯空白前后缀中取得唯一 JSON 对象。
- 对文档明确表示“缺省”的可选空字符串归一为字段缺失。
- 对数组逐项校验并保留身份明确的合法项。
- 生成准确 JSON path、类型、枚举、重复项、引用和作用域问题。

禁止免费“修复”：

- 猜测缺失的人物、事件、转折或 ID。
- 自动重排无法证明顺序的情节。
- 将自然语言强行解释成正式结构并直接采纳。
- 删除冲突事实后假装候选完整。

一次定向修复只发送：原输出、稳定错误代码与 path、目标最小 schema、必须保留的字段 hash、禁止改动的
正式事实。不得重新发送整份世界资料或让模型自由重写所有内容。

## 10. 上下文优先级

生成规划和正文时按下列顺序分配注意力与预算：

1. 作者本轮明确要求。
2. `NarrativeBrief`、章任务、场景目标和退出变化。
3. 直接前文、当前角色状态和未完成动作。
4. 与本次任务直接相关的 Canon 硬约束。
5. 相关世界背景、角色资料和 Codex。
6. 作者风格和其它低优先级参考。

现有大体量世界观、角色和 Codex 来源不能因为内容更多就压过叙事任务。世界信息只有在影响人物选择、
冲突或结果时进入正文；禁止把“读取到”误解为“必须复述”。

## 11. 施工单元

### CREL-0：基线、文档与特性开关

- 保存 H86、CI、E2E 和 AI census 基线。
- 新能力使用版本化本地开关，默认先限故事线 development。
- 完成本文档、路线图活动卡和回滚说明。

完成门：关闭开关后恢复 `f7300b0` 行为，旧 Run/候选可读。

### CREL-1：统一创作产物合同

- 实现状态、问题、片段、假设、调用和修复证据的 parser/serializer。
- 扩展 `MasterCandidatePayload`，纳入 hash、stale 和持久化校验。
- 不新增表。

完成门：伪造状态、倒退用量、未知问题动作、跨候选 repair hash 全部被拒绝。

### CREL-2：产物级预算与停止政策

- 增加质量模式和每产物 1+1 调用政策。
- 区分首次生成、定向修复、作者触发评审。
- durable 恢复不得产生隐藏第三次调用。

完成门：协议失败、同指纹、网络未知、非重试 4xx、预算耗尽均有反例。

### CREL-3：免费归一化和精确问题定位

- 实现通用 JSON envelope normalizer 与领域 fragment parser 接口。
- 只允许白名单语义无损变换。
- 保留原始 hash、归一化步骤和问题路径。

完成门：有效围栏/可选空值可恢复；多对象、注入文字、语义缺失不被误救。

### CREL-4：一次定向修复

- 由稳定错误代码生成最小修复请求。
- 不向模型泄漏内部异常、隐藏标签或不相关项目资料。
- 修复成功、部分成功和失败都形成 CreativeArtifact。

完成门：同一产物最多两次调用；第二次仍失败进入 `manual-repair`。

### CREL-5：统一候选结果界面

- 展示状态、问题位置、假设、调用、token、预计费用和修复原因。
- 支持编辑、拒绝、接受警告、只处理合法子集和作者显式修复。
- 刷新后状态完全恢复，不重复调用。

完成门：通用副驾和故事线面板使用同一展示组件/读模型。

### CREL-6：故事线纵向切片

- `outline.story-arcs` 使用对象级结构输出和通用 normalizer。
- 单条故事线或阶段可形成合法片段；软问题不整批阻断。
- 最终采纳仍要求被选故事线整体结构合法。
- 新 development/holdout 不复用 H86 已消耗样例。

完成门：同模型新旧 A/B 达到本文件 3.2 首个社区体验门，或诚实保持发布关闭。

### CREL-7：NarrativeBrief 与部分设定脚手架

- 从现有输入确定性提取已知项，缺失项由同一次领域生成提出 provisional 假设。
- 支持快速草稿和引导创作两种入口。
- 临时假设随候选和后续 Run 传递，但不进入 Canon。

完成门：只有世界观/只有角色/只有概念样例均能形成冲突、目标、代价和下一步压力。

### CREL-8：主线到场景的规划链适配

- 复用现有故事核心、故事线、角色驱动方案、卷纲、章纲和细纲 Skill。
- 每层携带上游正式事实、临时假设和本层状态变化。
- 不重复生成已有内容，不改已写正文。

完成门：新项目能够从部分设定生成可编辑主线、章纲和场景卡，刷新可继续。

### CREL-9：正文有界质量闭环

- 复用现有正文 durable 主路径和 `review -> revise -> review`，改为默认无自动语义循环。
- 正文优先人物目标、行动、阻力、选择和退出变化。
- 本地检查重复、字数、引用、禁写边界和无事件推进。
- 语义评审与段落修订由作者显式触发。

完成门：部分设定样例不会只写世界观说明；修订只改选中问题/段落。

### CREL-10：作者偏好收口

- 复用现有 style learning、反馈和修订对。
- 区分本章、本作品和长期偏好；长期保存必须作者明确确认。
- 模型自己的输出不能自动成为作者风格。

完成门：偏好可见、可删除、可关闭，并有作用域与 stale 测试。

### CREL-11：长篇连续性收口

- 复用章节记忆、handoff、摘要、检索、影响图和章后 Run。
- 临时假设可确认、拒绝、过期；被拒绝后不再进入下一章。
- 连续 8～12 章不重复发送全书，不自动级联重写。

完成门：三种题材各完成连续章节验证，包含中途修改角色目标/设定/章纲。

### CREL-12：完整用户体验

- 在开始前显示计划、产物和最大调用数。
- 提供节省/均衡/精修模式、进度、停止、恢复和费用历史。
- 显示本章使用某项设定的原因和本章发生的状态变化。

完成门：新用户从一个想法到首章候选无需理解 Agent/Harness 内部术语。

### CREL-13：评测体系

- 新建 development、sealed holdout、控制样例和长篇目录。
- 同一模型、温度、输入和近似预算配对比较新旧路径。
- 指标覆盖可编辑产物率、丢弃率、保留比例、修改时间、推进、贴合、成本和延迟。
- 人工盲评与机器统计分离；机器不能代替作者主观接受度。

完成门：artifact 可验签、逐调用 usage 完整、失败不被删样、heldout 一次性运行。

### CREL-14：社区体验发布门

## 12. 测试矩阵

### 12.1 合同与反例

- 旧候选兼容、候选 hash、用量单调、修复绑定、问题闭集。
- 围栏、前后缀、多个 JSON、非法类型、可选空值、缺失必填、重复项。
- 合法/非法片段混合、全部非法、原始草稿过大、注入文本。
- 同指纹两次、第三次调用企图、恢复重放、服务商结果未知。
- 跨项目/World/Work、导入取消、stale、正式数据漂移和 terminal 撤销。

### 12.2 用户路径

- 一个概念 → 故事线候选 → 警告 → 编辑 → 采纳。
- 部分世界观 → 临时叙事脚手架 → 章纲 → 场景 → 正文。
- 首次协议失败 → 一次定向修复 → 候选。
- 两次失败 → `manual-repair` 原始草稿 → 作者手改 → 重新本地验证 → 采纳。
- 中断/刷新 → 恢复同一结果和用量。
- 长篇中途改设定 → 影响分析 → 作者处理 → 下一章适配。

### 12.3 交付闸门

每个 CREL 单元先跑定向测试。提交前至少运行：

```bash
npm run check:architecture
npm run check:required-tables
npm run check:ai-manual
npx tsc --noEmit
npm run build
```

交付单元运行 `npm run ci`；适用时运行 `npm run ci:e2e` 和隔离浏览器真实 API 验证。
