# StoryForge 分支、PR 与交付协作流程

> 版本：2.2.0 · 生效：2026-10-23 · 权威层级：L1
> 适用于人类与任意编码/审查 Agent，不绑定某两个模型。

## 1. 基本原则

- 一个工作树同一时间只有一个写入者；并行任务使用独立 clone 或 `git worktree`。
- 一个分支承担一个可解释的产品增量，名称使用 `feat/`、`fix/` 或 `refactor/`。
- 不直接 push `main`；不 force push 主干；不覆盖他人未提交改动。
- 交接单元是分支 + commit + PR + 验证证据。临时对话和施工流水不进入现行规范文档。
- `main` 无 staging、可直接发布，因此合并串行进行。

## 2. 开工

1. `git status --short --branch`，确认工作树与 owner。
2. `git fetch --all --prune`，核对目标基线和相关 PR。
3. 从最新 `origin/main` 创建独立分支/工作树。
4. 按总纲和产品契约写开工卡，建立三注册表与测试闭包。
5. 若发现当前分支含另一主题的领先内容，先拆分或明确依赖，不继续堆叠。

### 2.1 并行产品分支的基线与冲突区

并行开发短篇、剧本、漫画、跑团、角色聊天或文字游戏时：

- 先合入或依赖同一个架构治理基线；产品分支不得从治理前的旧身份、旧 WorldRelease 或世界直达 runtime 路线继续扩建。
- 独立产品文件可并行修改；`AGENTS.md`、`CLAUDE.md`、总纲、三注册表、schema、世界网关、跨产品逻辑契约、产品目录、包管理锁文件属于集成热点，不由多个产品分支无协调并改。
- 剧本与漫画若同时需要修改 adaptation 公共来源/Brief/manifest，先拆出一个共享底座提交；剧本场次与漫画页格/媒资继续留在各自分支。
- 跑团、聊天和文字游戏只在各自目录增加 requirement adapter 和产品 owner 数据；若需要改变中立 `describe/search/read` 协议，先以独立共享契约变更证明向后兼容。
- 节点模式与分步骤共用正式领域 action。任何节点分支修改长篇 Skill、Context、Adoption 或 Canon schema 时，必须与长篇调用方一起验证，不能只跑节点测试。

推荐集成顺序是：治理基线 → 必要的共享 schema/契约小提交 → 各产品分支。每个后合并分支先同步最新集成树，再解决真实语义冲突并重跑验证；不能把“Git 能自动合并”当作架构兼容证明。

### 2.2 总纲与本地 API 治理分支

当前专用分支为 `feat/project-governance-api-20261023`。它从最新 `origin/main` 建立，持续维护项目总纲、文档权威、公共开发规则及 [本地 API 配置规则](./LOCAL-API-CONFIG.md)。分支负责人维护这些共享约束；具体产品实现及产品专用方案仍由对应产品分支负责。

- 治理变更形成独立、可审查的文档提交，标明受影响的契约与调用方；分支名本身不赋予未提交草稿权威。
- 产品分支开工、遇到契约变化及交付前，核对治理分支的明确提交 SHA，记录所依据的总纲版本和治理提交。共享规则有冲突时先在治理分支裁决，再继续受影响的开发。
- 已合入 `main` 的治理提交随最新主干同步。确需提前依赖尚未合入主干的文档提交时，在依赖分支中明确记录该 SHA，通过普通 merge 或选定文档提交的 cherry-pick 引入并解决冲突；不得从移动中的分支头复制片段后称为已同步。
- 同一机器上的各工作树按统一路径读取仓库外 API 索引；不得把真实配置、凭据或指向它们的符号链接复制进任何分支。其他机器需单独配置，Git 同步不承担密钥分发。
- 本分支的私有配置登记与修改由单一维护者串行进行；使用方只按任务范围读取，不自行改写公共配置。发现缺项、漂移或失效时反馈给治理维护者。
- 治理分支定期以普通 merge 同步最新主干；审查、PR、合并和发布仍按本文执行。治理分支不是另一条生产发布线，不直接覆盖其他工作树。

## 3. 提交

- 提交只包含当前任务的代码、测试和必要文档。
- 提交前查看 `git diff --stat`、`git diff`、`git status` 和 `git diff --check`。
- 不用 `git add -A` 掩盖未知文件；明确添加目标路径。
- 生成文件通过官方脚本重建，不手工解决内容冲突。
- commit message 说明任务/产品、完成边界；验证摘要写入 PR。

## 4. PR 描述

PR 至少包含：

- 总纲章节、产品与用户结果；
- 范围和非范围；
- 数据/AI/表/版本/媒资影响；
- 新旧入口变化；
- 正反例、CI/E2E 命令与结果；
- 风险、迁移、回滚或恢复方式；
- 尚未完成项，不用“完整”“商业级”等超证据措辞。

## 5. 审查

审查者基于最新 head：

1. 先检查产品边界和数据 owner；
2. 再看入口 → 读写 → 生命周期 → 下游 → 测试；
3. 优先报告数据丢失、权限/作用域、stale、恢复、重复入口与错误完成状态；
4. 运行风险相称的验证；
5. 评论应定位文件/行和可复现后果，不用仅表达偏好。

修复进入同一分支或明确 follow-up；未解决的高风险问题不能只写文档后合并。

## 6. 合并 main

标准 `CI` 在两个独立环境中分别完整运行 `npm run ci` 和 `npm run ci:e2e`，避免整库覆盖率与
浏览器检查串行累加超过单个 runner 的执行时限。浏览器环境先独立构建并运行生产版模型与嵌入代理检查，
保留截图和 trace；两个环境都记录实际检出的不可变 SHA。`verify` 只有在两项完整检查都成功时才通过，
失败、取消或跳过均不能成为通过。原 `full-delivery` 标签工作流已收口，不再重复执行同一轮整库检查。
每次 head 更新需要核对对应 SHA 的新结果，不能用旧结果宣称新提交通过。

1. 获取最新 `origin/main`，确认没有新的生产提交遗漏。
2. 通过普通 merge/rebase 解决冲突；不丢双方功能、注册表、迁移或测试。
3. 在最终合并树运行 `npm run ci`；适用时运行 `npm run ci:e2e`。
4. 确认 PR head 的独有提交是 main 祖先或被有证据地等价重实现。
5. 使用普通 push 更新 `main`；禁止 force。
6. 拉取远端并验证本地/远端 SHA 一致。
7. PR 合并后再删除已合并本地/远程分支与多余工作树。

## 7. 多分支总整合

需要把多个历史分支收敛到主干时：

- 先枚举本地 refs、remote refs、PR heads、worktrees 和 merge-base；
- 为每个分支记录独有提交、文件、与其它分支的重叠和处理结论；
- 逐个正常 merge，冲突按当前总纲、数据安全和最新实现裁决；
- 每个 head 只有在成为整合分支祖先或等价内容有逐项证据后才标记已整合；
- 完整验证、push main、PR 状态确认后才清理 refs；
- 最终断言只剩本地 `main` 和 `origin/main`，SHA 相同且工作树干净。

## 8. 工作树与依赖

- 不把 `node_modules` 符号链接或构建产物提交进 Git。
- 独立 worktree 可共享包缓存，但安装状态和生成缓存不得污染仓库。
- 移除工作树前确认 clean、提交已在目标主干、没有唯一 untracked 文件。
- 分支删除优先 `git branch -d`；若 Git 判断未合并，先调查，不以 `-D` 跳过证据。

## 9. 外部阻塞

外部 provider、依赖审计、GitHub 或部署不可用时，保留本地完整验证和错误证据，明确哪些门未完成。不能把“本地部分通过”写成主干全绿，也不能因外部阻塞扩大未授权远程操作。

## 10. Bug 收集、修复与发行闭环

GitHub Issue 是可持续核对的问题队列。官网反馈、管理后台的“Bug 与建议”和错误报告均须纳入；本地巡检台账只用于去重与恢复，不能替代仓库进展和后台处理记录。

1. **收集与去重**：每次获取最新主干、全部未关闭 Issue、未解决后台反馈和新增错误组，核对已有 PR、实现及正式发行。按版本、平台、入口、错误特征和复现区分问题；旧版本上报、重复上报或仅有异常中断标记不能直接判断新版本缺陷。已有同一问题关联原 Issue，不重复建单；未确认同根因的错误分别保留证据。
2. **建立工单**：官网公开 Issue 直接跟进；后台私人反馈由维护者提炼成脱敏技术摘要后创建或关联 Issue。公开内容只包含复现所需的版本、操作、技术现象、已确认根因与验证；不公开原反馈正文、联系方式、安装标识、私人编号、附件、手稿、模型原文、完整路径或凭据。敏感信息不足以安全提炼时，建立说明证据待补的技术工单，原证据保留私有。功能建议与部署评估标明类型，不按 Bug 擅自扩展功能。
3. **公开进展**：首次排查、发现阻塞、修复 PR、验证完成、发行和结案均更新 Issue；写明已确认事实、未确认项、下一步及负责人。后台可编辑的处理记录同步 Issue/PR 链接、受影响版本和结论，并保存后读回；写入失败在 Issue 说明“后台同步待完成”，恢复认证后补写。错误聚合无写入接口时，仓库工单为处理记录，不直接改运营数据库。
4. **修复与验证**：在独立 `fix/` 分支保留修改前复现或可靠证据，遵循本文件既有验证和 PR 规则。未复现、缺原环境或外部依赖的问题保持开放，说明所缺证据和可执行的排查步骤，不以运行正常的另一条路径宣称原问题解决。
5. **交付到用户**：主干已合并、安装包尚未包含的状态写为“已合并，待发布”，关联目标版本。发行必须包含修复提交，通过现有发布、目标平台启动及覆盖升级验证，公开可下载附件和校验信息；官网/README 下载入口核对至最新发行。不得覆盖旧正式附件或提前公开未验证的更新元数据。
6. **结案与复发**：核对修复 PR、最终验证、实际发行提交/附件与适用平台后，向 Issue 写入发行链接、验收范围和恢复方式，再关闭；对应后台状态更新并读回。需求只在原范围验收或给出明确拒绝/重复理由后收束。新版本复发时重开原工单或建立有明确关联的回归工单，不能把记录过期或没有新上报视为已修复。

每项最低记录：来源类型、仓库 Issue、负责人、现象与受影响版本、证据状态、当前处理状态、下一步、修复 PR/SHA、验证、目标/实际发行、后台同步结果及结案理由。公开工单与私人反馈的精确映射仅保存在受保护的后台或仓库外私有台账中。
