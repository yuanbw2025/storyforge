# StoryForge 全项目架构与质量审查计划

> 版本：1.1.0 · 日期：2026-10-29 · 层级：L4 审查执行计划
> 当前状态：计划已修订，Q0～Q7 均未开始，G1 首轮开发放行尚未评估；没有形成项目质量结论。
> 本轮交付仅为计划修订。实际审查在用户明确启动后执行；执行期间可将已授权的阻塞修复提前安排为独立任务。

## 1. 目标、依据与任务边界

本计划回答三个问题：StoryForge 的架构是否合理、代码是否容易正确维护、各项已承诺能力是否具备可靠交付证据。架构与代码质量分别形成结论，同时审查数据、安全、AI、用户流程、性能、发布和开源维护能力。

审查以当前明确承诺的能力为对象。已经验收的能力优先复证，不因未来目标未完成而整体降级；实验性与计划中的能力检查门控和声明，不按正式功能缺陷计数。商业质量要求用于判断工程和产品的可靠程度，不要求本轮实现计费、云同步或其它后置业务。

依据按以下顺序使用：

1. [项目总纲](../PROJECT-MASTER-CHARTER.md)：产品边界、两条生命周期、S1/S2/S3、数据归属和发展顺序。
2. [开发入口](../../AGENTS.md)、[上下文路由](../CONTEXT-ROUTING.md)、[当前架构](../ARCHITECTURE.md)、[数据治理](../DATA-GOVERNANCE.md)、[Harness 标准](../HARNESS-QUALITY-STANDARD.md)、[工程质量标准](../ENGINEERING-QUALITY-STANDARD.md)。
3. [现行产品契约](../products/README.md)、[能力基线](../roadmap/CAPABILITY-BASELINE.md)和各产品专项计划。
4. 三注册表、schema、类型、真实入口、测试和当前运行证据，用于确定实现事实。

本计划不修改上位契约，不降低既有 CI、数据或发布门槛。历史审计只能提供待复核线索；过去的问题、分数、版本号、检查结果不得直接转为本轮结论。

执行采用“优先审查共享底座与相关代码热点、独立任务有限并行、阻塞修复先集成、产品增量小步跟进”的顺序。首轮先交付后续方向的开发边界，无需等全项目所有问题修完；Q0～Q7 的全量覆盖、独立架构报告和代码质量报告仍须完成。

开工卡：

| 项目 | 本计划约定 |
|---|---|
| 产品与生命周期 | 全项目工程审查，属于产品能力研发；具体作品生产只在隔离验收夹具中观察 |
| S1/S2/S3 | 检查世界衍生产品的全部阶段及交接；独立产品按自己的生产、版本与运行链检查 |
| 数据归属 | 作者数据保持原 owner；审查夹具、日志和结果与作者项目隔离 |
| 交接物 | 版本化范围表、覆盖矩阵、证据索引、问题清单、G1 放行记录与任务分类、已验证底座记录、架构报告、代码质量报告、总报告及整改顺序 |
| 世界引用与媒资 | 验证冻结引用和原产品归属，不迁移或接管真实世界、作品、媒资、Release 或存档 |
| 执行边界 | 审查使用只读追踪与隔离验证；阻塞修复、开发、合并按独立任务和已有授权执行。本次修订不启动这些工作，也不部署、发布或写外部工单/通知 |

## 2. 基线与环境

计划编制参考提交为 `c5b51da301abd3875b26732d9657ad485ad39105`。它只说明编制时参考的代码版本；正式审查的 `auditBaseSha` 仍为待定。

Q0 必须重新获取并固定主干，并为本轮纳入的开发批次划定明确截止点。范围内的未合并工作逐项记为：等待整合、明确排除、单独审查；不要求清理无关工作树，也不把未合并分支内容算作主干能力。若约定纳入的一批开发尚未收束，先取得其范围处理结论；新出现的支线登记为后续增量，不自动推迟已固定的审查起点。

每个运行批次记录：`auditId`、`auditBaseSha`、测试补丁 SHA（如有）、日期、Node/npm/操作系统、锁文件 hash、依赖安装方式、浏览器/设备、夹具 hash、命令、退出码、结果和证据位置。测试探针与基线源码分开标记；包含探针的树不能冒充原始主干。

开发与审查并行时，区分以下提交：

| 记录 | 含义与约束 |
|---|---|
| `auditBaseSha`（A） | 原始审查基线，固定后不随主干移动；原始问题和报告始终保留 A |
| `verifiedFoundationSha`（B） | 纳入相关阻塞修复后，在实际集成树完成规定复验的不可变提交；若无需修复且证据充分，可为 A。另记已覆盖范围、遗留项及是否已进入主干 |
| `taskBaseSha` | 开发任务实际起点，明确是否包含其所需 B；依赖未合并的基础提交时显式记录依赖和集成状态 |
| `integrationHeadSha` | 每次候选合并的实际集成树，按现行协作规则完成相应 CI、生命周期和纵切面验证 |

主干新增变更逐项记录与 A/B 的差异：不受影响范围可保留原证据，受影响范围补审和复验，并更新对应放行记录。无需重做所有无关审查；A 的通过结果也不能直接覆盖之后的提交。B 表示已验证的具体范围，不代表其整棵代码树完成全量审查或正式发行。

执行环境要求：

- 审查过程保护当前工作树、其他任务和未提交内容；不为同步或验证便利 reset、stash、覆盖、清理或自动解决合并。独立修复/开发与正常集成按 4.3 及已有授权执行。
- 使用独立审查工作树或仓库外的同 SHA 快照。依赖、构建和覆盖率缓存独立，不改共享 `node_modules` 或锁文件修复环境。
- 浏览器使用全新测试 profile/context、隔离 origin 和数据库；不得接管作者当前浏览器项目、存档、设置或模型连接。
- 用原创合成数据、受支持旧版本夹具、损坏夹具和独立媒资；真实用户数据须另行明确范围并保留可恢复副本。
- 真实模型与媒资测试在明确 provider、允许用途、合成输入、调用/费用上限后执行；配置可读不代表批量调用授权。缺少条件则登记待验证，继续独立工作。
- 凭据、私有端点、账号、主机、用户反馈原文、手稿和未脱敏响应留在仓库外受保护位置。Git/报告只保存必要的脱敏索引、hash 和可公开复现材料。

全量覆盖的含义：生产源码、构建/运行脚本、配置和公开入口全部纳入清单与适用静态检查；每个产品和共享模块都有明确审查记录；每条高风险写入与生命周期路径建立关联闭包。历史原始证据、生成物和第三方代码按来源单列，不用其体量抬高已审查比例。

深读优先级：数据/权限/版本/正式 AI 路径 → 跨产品共享热点 → 最近频繁修改且复杂的模块 → 其余生产模块。每个模块至少有一次基于实际行为的结构审阅；对低风险模块采用的抽样必须记录选择依据、遗漏路径与剩余风险，不能把“全仓扫描”写成“逐行审完”。

### 3.3 覆盖矩阵

每个产品/共享模块一行，至少包含：

`对象 ID｜承诺/成熟度｜入口及深链｜owner｜读取｜候选/写回｜表/文件生命周期｜下游｜架构｜代码｜数据/AI/安全｜用户流程｜性能/体验｜发布/文档｜证据及 SHA｜遗留项｜关联开发任务/G1 范围与条件`

## 4. 执行阶段与检查点

Q0～Q7 是审查阶段编号，与产品 S1/S2/S3 无关。先审共享底座，再逐产品验证；发现高风险证据时优先收敛受影响路径。G1 是首轮开发放行检查点，不替代这些阶段，也不提升产品成熟度。表中所有任务当前均为未开始。

| 阶段 | 工作项 | 前置 | 阶段交付与退出条件 |
|---|---|---|---|
| Q0 固定范围与环境 | Q0-01 主干/分支范围；Q0-02 不可变 SHA；Q0-03 隔离环境与数据/调用边界 | 用户明确启动审查 | 基线记录、纳入/排除清单、隔离证明；范围内未整合内容已有明确处理方式 |

| Q6 交付与开源维护 | Q6-01 完整 CI/E2E；Q6-02 发布/升级/恢复；Q6-03 供应链/许可；Q6-04 文档/贡献/维护 | Q1 起收集，Q4/Q5 后汇总 | 同 SHA 验证摘要、平台/发行证据、供应链与开源维护清单；外部阻塞逐项保留 |

Q2、Q3 是独立重点，不能被一次 CI 代替。Q6 中廉价的静态门可在 Q1 提前运行以建立基线；最终完整结果仍须绑定相同审查 SHA。无源码或环境变化且结果有效时复用证据，不为补进度重复跑相同检查。

Q1 后依据实际模块、路径和测试耗时估算首轮检查点与全量审查的批次和工期；本计划不预设未经盘点的“几天全审完”。每阶段完成提供范围、发现、证据、阻塞和下一步；长阶段按产品或共享模块分批交付。

### 4.1 首轮开发放行检查点 G1

执行顺序为：Q0/Q1 → 优先完成相关范围的 Q2/Q3 与 Q4 验证 → 已授权的阻塞修复及复验 → G1 给出分范围开发结论 → 继续 Q2～Q7 的剩余审查与获准增量。无相关依赖的准备任务可以同时进行。首轮相关范围完成不把整个 Q2/Q3/Q4 标记为完成。

首轮至少检查后续方向依赖的产品边界与数据 owner、三注册表、schema/迁移、共享 Harness、保存/失败恢复，以及这些路径的复杂度、并发、异常和测试热点。范围以实际入口、共享调用方和下游依赖闭包确定，不能仅检查计划中的新功能文件。

G1 按具体范围记录以下条件：

1. Q0/Q1 基线、范围、隔离环境与任务依赖记录齐备。
2. 相关架构和代码质量审阅已有证据，关键写入、版本、权限与生命周期正反例已验证；决定该范围正确性的必需证据不能以受阻或待验证代替。
3. 没有影响该范围的未解决 P0/P1，且归属、共享接口、迁移、恢复等关键决策已明确；其他无关范围的问题单独限制。
4. 有修复时，原反例、受影响调用方/下游及现行质量门已在实际候选集成树复验，记录 B；无需修复时也须提供对应验证依据。
5. 给出可继续范围、明确排除范围、剩余风险、依赖 B、失效条件和后续验证要求。每个开发任务对应三类结论之一，不提供全项目笼统放行。

如果条件不足，先交付具体阻塞问题、所缺证据和下一项交付物；不为赶时间降低门槛，也不要求所有无关任务一起停工。G1 只支持范围内的开发安排，不构成合并、发布或商业质量接受。

### 4.2 并行任务分类与开工条件

| 分类 | 判定依据 | 允许推进的内容 | 后续条件 |
|---|---|---|---|
| 可以继续 | 相关边界已明确，依赖与影响可追踪，无阻塞问题，可独立验证 | 需求/研究/样本等独立准备，或已评估范围内的产品增量 | 按任务卡记录依赖与允许改动；合并仍须满足 4.3 |
| 满足条件后继续 | 依赖具体接口确认、基础修复或必需验证，完成条件明确 | 独立的需求、设计、合成样本或与正式数据隔离的原型 | 记录阻塞 ID、责任人/角色和下一交付物；条件满足后更新分类再推进依赖实现 |
| 暂缓相关实现 | 关键归属/权限/迁移/恢复问题未裁决，或相关 P0/P1 尚未解决 | 问题复现、影响分析和方案比较 | 相关问题修复/决策并复验后重新评估 |

分类看实际依赖，不按“UI”“局部”“AI”等名称判断。UI 工作若改变路由、共享状态、保存/采用或恢复，需要审查相应边界；既有稳定契约内的产品专属 AI 增量也可按证据列为可以继续，不一律等待全项目审查。

没有依赖记录或存在未知共享影响的任务先补齐分类依据；不能默认它不受审查影响。尚未完成 G1 时，可以凭明确独立性证据开展准备任务，但本轮计划修订不实际启动任何开发任务。

独立准备任务确实不依赖 B 时，记录为不适用并说明理由；不虚构已验证底座，也不把准备任务的分类结论解释为正式运行代码已审查。

### 4.3 合并条件、共享热点与放行失效

可以开工的任务，在合并前仍须同步其所需的已验证底座，核对审查新增结论，并在最新实际集成树完成现行规定的 CI、相关生命周期与必要产品纵切面验证。不能以 G1 记录、旧 SHA 的通过或 Git 无冲突代替合并条件。

每个分支/工作树保持一个写入者和一个可解释增量。schema、三注册表、世界网关、共享 Harness/跨产品协议、产品目录和锁文件等共享热点先拆成独立基础提交，按现行总纲与协作规则串行验证、集成，再让产品分支同步；不得在多条产品分支各维护一套协议。依赖未合并基础提交的分支明确记为待底座先行集成。

任务超出已评估范围，改变 owner、正式写回契约、迁移或共享协议，或新增问题推翻原结论时，相关放行记录失效，暂停对应依赖实现并补审、复验和更新分类。无关范围的记录保持。主干更新同样按实际差异评估，后合并分支及时同步、小步集成，避免等全部功能做完后一次性处理兼容性。

阻塞修复可以在 Q7 前形成独立任务并在已有授权内推进；审查原基线保持可追溯，修复不混入并行功能批次。修复、集成和外部发布各按现行协作规则及已有授权执行，本计划不自行扩展权限。

## 5. 两项核心审查的方法

### 5.1 Q2：架构是否合理

- **产品与归属**：区分产品研发和具体作品生产；核对 Project 壳、Work、World、产品实例、媒资与 runtime 的唯一 owner；检查镜像、双写、回退读取和隐式同步。
- **分层与依赖**：绘制实际依赖图，定位循环、跨层写入、跨产品内部依赖、重复服务、共享模块反向依赖 UI；结合调用方判断修改的影响范围。
- **三注册表**：逐类追踪上下文读取、正式 AI 写入、表和外部对象生命周期；查找绕过 Gateway、adopt、领域事务或注册生命周期的入口。
- **长篇与节点**：对照 action/Skill/Context/Adoption/记忆/Canon，验证两种入口复用同一领域能力；节点运行记录不得形成第二套作品事实。
- **世界衍生产品**：验证 S1 世界封存、S2 产品定向、S3 产品执行；追踪开始授权、WorldReference、Brief、冻结 SourcePlan、实际 Context Manifest、SourceManifest 和 ProductRelease。
- **冻结与执行**：核对 describe/search/read、产品需求适配器、原文证据、版本/hash/权限、release 与 session 绑定；确定性约束不得只依赖 Prompt；产品运行不得回写冻结世界。
- **真实入口与例外**：同时检查导航、直接 URL、页面、服务调用和导入恢复；旧入口是否收口，实验性开关是否失效关闭；例外是否足够窄且有退出条件。
- **适度复杂度**：检查现有抽象是否减少重复、是否存在无真实消费者的平台层；架构评价基于当前需求和变化成本，不以层数或微服务数量打分。

每条重要路径建立：`入口 → 读取来源 → 候选/写回 → 生命周期 → 下游 → 测试/运行证据`。报告同时记录已守住的边界与偏差，附模块图、归属表、风险和最小整改方向。

架构报告分别给出“契约符合性”和“设计适用性”：后者说明边界、复用、依赖、复杂度与恢复成本是否适合真实需求。现行契约本身存在必要性、可实现性或成本疑问时，形成有证据的修订建议并标记需决策；实施仍服从现行权威。

### 5.2 Q3：代码是否容易正确维护

- **结构**：单一职责、命名、函数/组件边界、领域与 UI 解耦、配置集中度、废弃实现和兼容分支。
- **复杂度**：函数分支、嵌套、状态组合和文件规模；结合近 90 天变更频率、缺陷关联和依赖影响选择热点。大文件或复杂函数先作为审阅线索，不自动判为缺陷。
- **重复**：同时检查文本相似和语义重复，重点识别同一业务规则在多处独立维护；合理的产品差异不强行抽象。
- **类型与输入**：不安全断言、any、隐式 null、枚举/状态穷尽性；API、模型、导入、存储记录是否有运行时校验。
- **状态与并发**：重复提交、乱序响应、切换项目/作品后的旧回调、取消与删除竞态、多窗口更新、缓存失效、幂等与事务边界。
- **异常与资源**：错误分类、吞错/假成功、有限重试、未知结果、订阅/事件/定时器清理、Object URL/文件/大对象回收。
- **测试真实性**：断言可见结果和持久化后果；反例是否能使错误实现失败；mock 是否遮住实际 owner、事务、版本或网络边界。

对每个热点输出具体行为、位置、影响与修复收益。无法复现的疑点保留为待验证，不把偏好的命名/拆文件方式升级为严重问题。报告给出热点清单与维护优先级，不能仅列 lint 数量。

代码质量结论同时回答“是否满足工程底线”和“是否具备优秀的可维护性证据”。后者结合规则集中程度、理解与测试成本、常见变更的影响范围、故障定位和技术债趋势说明；只通过检查器时，保留对维护质量的评价边界。

## 6. Q4～Q6 专项验收清单

### 6.1 数据、AI、安全与恢复

| 专项 | 必测正反例 | 通过依据 |
|---|---|---|
| 保存与并发 | 人工保存/自动保存后刷新；失败/重复点击；乱序写入；切换 owner；多窗口冲突 | 内容与 revision 一致；失败可见；无静默覆盖或跨 owner 写入 |
| schema/迁移 | 空库、当前库、所有声明支持的旧版本与分支变体、损坏/未来版本、升级阻塞 | 受支持数据与引用保留；不支持输入明确拒绝且不改原库 |
| 导入导出 | 完整往返、冲突重映射、缺表/缺字段/未知字段、篡改、重复导入、超限与事务失败 | 内容/关系/hash/归属符合契约；原子提交；旧完成历史和可恢复运行正确区分 |
| 删除与文件 | 项目/世界/作品/实例删除、共享媒资、冻结版本强引用、Blob/OPFS、失败中断 | 无误删、孤儿或永久泄漏；恢复与保留策略可解释 |
| AI 读取 | 缺必读、权限外资源、错误世界/版本、未来知识、长尾事实、预算不足 | 来源与实际 manifest 一致；必读和禁止规则由代码执行 |
| AI 输出与采用 | 原始响应、非法结构、超长、候选编辑、拒绝、stale、采纳、post-state 和下游 | 原输出保留；只在明确确认与合法权限内原子写回；实际结果与回执一致 |
| durable 恢复 | 请求前/后崩溃、结果未知、超时、离线、取消、预算不足、认证/余额/非重试 4xx | attempt/checkpoint 可解释；无隐藏重发、重复计费或虚假终态 |
| 输入与权限 | 恶意 Markdown/HTML/URL/文件名/压缩包、模型提示注入、插件/桥接/社区越权 | 内容无法扩大工具或写权限；边界失败时关闭；导入不自动执行代码 |
| 隐私与凭据 | 配置、日志、错误报告、截图、导出、外部上下文和本机接口 | 无不必要内容外发；敏感值不进入 Git/公开证据；本机能力权限明确 |

故障注入只作用于隔离夹具和审查环境。审查遇到真实数据风险、凭据泄露或无法裁决的契约冲突时停止受影响的操作，保存脱敏证据并提出具体决策点；无关只读工作可以继续。

### 6.2 用户流程、性能和体验

每个承诺的产品主路径至少覆盖：首次进入、创建/选择、生产/编辑、确认/采纳、保存、退出/刷新恢复、修订、版本/导出；有 runtime 的产品还须验证发布绑定、开始、存档、恢复和升级兼容。所有适用路径补空态、无 API、离线、失败、取消、重复操作和跨 owner 切换。

长篇和节点复核相同产物的跨模式行为；世界衍生产品从冻结来源到产品运行完成纵切面；现有模板、入口和关键写域逐项登记覆盖，不以少数示例代替全部高风险路径。

规模采用小型夹具、声明的目标规模和接近已声明上限三档。长篇沿用当前标准的 10 万/30 万/100 万字符或等价夹具；世界、媒资、运行历史按各自契约和现有预算固定数量。记录冷/热启动、P50/P95、样本数、内存峰值、存储增长、取消响应和环境；模型网络耗时与本地处理分别统计。先引用已有性能预算，缺少预算时明确提出待确认值，不能测完后为结果降低阈值。

体验检查加载/成功/失败反馈、候选与正式内容区分、stale/来源可见、危险操作恢复、标签和错误定位、键盘/焦点、目标桌面与窄屏布局。自动检查与人工操作记录分开。

真实模型测试逐项固定任务、模型/版本、输入、调用与费用上限、样本和判分规则；文本、图像、音频分别验收。生成器自评、fixture、合成音频和自动通关只证明各自范围。文学、视觉一致性、听感、独立玩家体验与长期创作须有对应人工或独立评价；未完成则保留待验证。

### 6.3 发布、供应链与开源维护

- **交付链**：核对 CI 触发、实际 SHA、必需检查、权限与产物来源；取消/跳过/旧结果不计通过；构建、部署、发行和用户验收分别记录。
- **升级与恢复**：在声明支持的平台验证安装、启动、覆盖升级、设置/数据/存档保留、离线和故障处置；源码回退与数据库兼容分别检查。缺设备保留平台待验证，不推定通过。
- **供应链**：生产与开发/构建依赖分开盘点，检查锁文件、维护状态、漏洞适用性、构建脚本、CI Action 权限/固定版本、更新完整性、SBOM/来源证明是否存在。
- **许可与来源**：源代码、依赖、字体、图片、音视频、模型产物及插件分别核对来源、许可证、归属和再分发声明；无法确认的项目登记待核实，不给出未经依据的法律结论。
- **开源协作**：从干净环境按贡献文档安装、运行与测试；检查安全报告渠道、Issue/PR 模板、维护职责、支持版本、发布说明与关键权限集中度。
- **文档一致性**：核对架构、能力基线、用户指南、schema/备份说明、AI Manual、路线图、下载/发行入口与实际支持范围；区分设计目标、分支实现、主干合并、部署和正式发行。
- **可观测性与运营**：操作/运行 ID、错误分类、版本、失败阶段和恢复说明应可追溯；若有运营数据，统计变更失败与修复时长。没有记录时标为无法评价，不推算零故障。

## 7. 指标、门槛与评价方式

下表定义采集口径，不填入未测得的分数。已有契约门槛保持；新增数值目标在测量前登记。复杂度、重复率和提交活跃度是诊断信号，不是自动质量结论。

| 维度/指标 | 采集口径 | 判定重点 |
|---|---|---|
| 范围覆盖率 | 有明确结果/阻塞/不适用理由的范围项 ÷ Q1 冻结范围项 | 报告交付时为 100%；受阻不等于验收通过 |
| 高风险路径验证率 | 已执行的关键正反例 ÷ 必须执行的关键正反例 | 未验证清单必须显式存在；发布接受所需项全部通过 |
| 开发放行记录 | 每个推进任务的分类、范围、依赖 B、阻塞/失效条件、证据与合并状态 | 待确认不计为放行；按任务检查，不用全局通过率掩盖阻塞项 |
| 架构违规 | 绕过注册表、越 owner/层、重复正式入口、版本/权限失守的数量与影响 | 逐项给证据；严重违规阻止受影响能力接受 |
| 依赖与变更影响 | 循环、跨产品内部依赖、关键公共模块扇入/扇出与变更联动 | 与业务边界及修复成本结合评价 |
| 代码热点 | 分支/嵌套/状态复杂度 × 变更频率 × 影响范围 | 形成深读与整改顺序；原始量纲分别保留 |
| 重复与类型逃逸 | 语义重复规则、不安全断言/any、外部输入未校验位置 | 按路径风险与分母报告，不用总行数稀释 |
| 生命周期通过率 | 保存/迁移/往返/重映射/删除/文件的适用正反例 | 受支持范围不得丢失或串改数据；失败须可恢复 |
| AI 权限与恢复 | 正式入口登记、实际 manifest、候选/采纳、attempt/receipt、stale/未知结果反例 | 证据闭环，禁止隐藏扩大权限与未知结果重发 |
| 测试有效性 | 关键分支覆盖、故障用例、断言后果、可疑测试的反例或变异探针 | 覆盖率说明 include/exclude；测试数量不代表行为覆盖 |
| 测试不稳定率 | 同 SHA/同环境存在不一致结果的运行 ÷ 可比运行 | 保留首次失败与重跑结果；禁止只报告重跑成功 |
| 缺陷逃逸 | 发布后确认缺陷及严重度、受影响版本和关联变更 | 无可靠发布/反馈记录则无法计算，不填零 |
| 性能与容量 | 固定夹具下 P50/P95、样本、内存/存储和已验证上限 | 使用声明预算；区分模型网络与本地耗时 |
| 用户任务成功率 | 各产品实际完成任务数 ÷ 同条件尝试数 | 按产品、任务、环境分别报告 |
| 可访问性与恢复体验 | 键盘/焦点/标签/窄屏/错误恢复的适用检查 | 核心操作可达，失败有明确可行动反馈 |
| 安全与供应链 | 已确认风险、依赖与 Actions 权限、来源/签名/SBOM 覆盖、修复时长 | 严重性结合可利用性；未查到不等于不存在 |
| 交付能力 | 部署频率、变更交付耗时、失败比例、恢复耗时和返工 | 固定统计窗口与样本；按系统趋势评价，不给个人打分 |
| AI 内容与成本 | 契约成功率、人工采用/修订、独立质量评价、单任务成本与时延 | 工程成功、内容质量、成本分别给结论 |
| 开源维护 | 干净环境上手结果、贡献/安全渠道、支持政策、许可完整性、维护集中风险 | 不以 Stars、提交数或下载量替代质量证据 |

每个维度与每个产品给出：通过、部分通过、未通过、证据不足、不适用；另给证据置信度。架构与代码质量分别说明优势、风险和维护成本。总报告不采用会掩盖数据/安全缺陷的加权平均分，也不在证据不足时宣称“商业级”。

## 8. 验证命令与执行规则

以下是未来审查的命令入口，本次计划修订不执行产品 CI、E2E、真实 API 或性能审查。Q0 在固定 SHA 后从该版本 `package.json` 再核对脚本；新增/删除脚本记录差异。

审查 A、阻塞修复 B 和后续候选集成树的结果分别记录；复用证据须说明差异与不受影响依据。G1 不跳过现行代码提交与合并检查，只调整审查覆盖和授权内整改的先后顺序。

| 层次 | 入口 | 证据要求 |
|---|---|---|
| 注册与结构 | `npm run check:architecture`、`npm run check:required-tables`、`npm run check:ai-manual`、`npm run check:ai-entry-registry` | 静态检查通过后仍要追踪真实入口、写回与恢复 |

| 文档与质量元数据 | `npm run check:docs`、`npm run check:roadmap`、`npm run check:agent-context`、`npm run check:agent-freshness`、`npm run check:canon-coverage`、`npm run check:project-metrics`、`npm run check:source-reachability` | 日期、清单或豁免不得为使检查通过而随意改写 |
| 依赖与代码检查 | `npm run check:dependencies`、`npm run lint` | 补充开发/构建依赖和实际输入边界审阅；不自动破坏性升级 |
| 测试与构建 | `npm run test:coverage`、`npm run build`、`npm run check:bundle-size` | 记录覆盖范围与构建目标；缺依赖属于环境证据，不自动判产品错误 |
| 完整工程门 | `npm run ci` | 报告整体退出结果；首处失败导致后续未执行项全部标出 |
| 隔离浏览器门 | `npm run ci:e2e` | 确认隔离 profile/数据库与目标 SHA，保留失败 trace/截图及跳过原因 |
| 专项与平台 | 当前产品专项性能脚本、客户端/分发测试、发布元数据检查 | 按声明支持范围运行；需要 tag/设备/模型/预算时先满足实际参数 |

若依赖审计受上游服务/公告阻塞，保留完整 CI 的失败状态，独立完成其余可运行门并单列结果；不能合成为“CI 全绿”。若全套结果已覆盖相同 SHA、环境和用例，复用相同证据，只有变更、失败或未决疑点才重跑。

## 9. 证据与问题台账

证据等级分别保存，不互相替代：代码/静态事实、确定性单元与集成、隔离浏览器流程、真实 provider、目标设备、人工内容/体验、部署/正式发行。每个结果注明实际证明什么及没有证明什么。

公开、精炼结果可在实施时登记为 L4 文档；长日志、构建产物、覆盖率明细、私有响应留在隔离证据目录。目录由 Q0 建立，不向 Git 提交真实配置。敏感证据只留引用与访问边界；新增现行文档同步文档权威索引与检查器。

问题记录模板：


| 优先级 | 影响判据 | 处理顺序 |
|---|---|---|
| P0 | 可导致不可恢复数据丢失/串改、凭据泄露、未授权敏感外发或严重执行越权 | 立即报告，停止受影响操作，保留恢复材料；阻止受影响范围发布 |
| P1 | 核心流程不可完成、重要归属/权限/版本边界失守、静默错误或恢复失败 | 优先形成最小修复与反例；阻止相应能力验收 |
| P2 | 局部功能、性能、体验或维护问题，有明确可接受绕行 | 按影响、频率与修复依赖排期 |
| P3 | 不影响当前正确性的整理、可读性与长期优化 | 记录收益，避免与高风险修复混批 |

严重度取决于实际后果；疑点不能自动记为已确认 P0。相同根因合并问题，保留全部受影响产品和复现；同一症状但根因未确认时不强行合并。契约冲突记为需决策，不用代码创建事实。

历史线索可包括 durable 恢复、原始响应、成熟度门、冻结来源语义、schema/备份文档、世界插件归属和 Skill freshness；Q1 从受版本控制的历史证据提取原问题及原 SHA，再在新基线逐项标为仍存在、已解决、范围变化或无法复证。本段不是当前缺陷清单。

## 10. 交付、进度与结束条件

实施后交付以下材料；名称为逻辑交付物，具体文件在执行阶段按文档治理登记，不在本轮创建空报告：

1. **基线与范围表**：SHA、环境、产品/模块、支持范围和明确排除项。
2. **覆盖矩阵与证据索引**：每项状态、实际执行、缺少证据和可复现位置。
3. **架构审查报告**：实际结构/归属/依赖/主链、正确边界、违规与演进成本。
4. **代码质量报告**：模块审阅、复杂度/重复/类型/并发热点与维护优先级。
5. **逐产品与专项结果**：数据/AI/安全/恢复、用户流程、性能、体验、平台和开源维护。
6. **问题台账与整改批次**：严重度、依赖、最小修复、负责人和逐项验收条件。
7. **总报告**：分维度与分产品结论、发布阻断、待验证/需决策事项及下一步。
8. **G1 与开发安排记录**：首轮相关范围、三类任务清单、阻塞条件、B 及集成状态、证据和失效/复评记录；在全量报告之前分批交付。

每批进度更新使用：`覆盖对象｜完成项与证据及 SHA｜新增/关闭问题｜开发分类与阻塞修复进展｜受阻/跳过及原因｜剩余范围｜下一批`。不得把“跑了多少命令”替代覆盖进度。优先交付决定后续方向能否推进的结论；G1 后继续按产品/共享模块交付剩余 Q2～Q7 范围，不无限延期全量报告。

审查完成条件：Q0～Q7 的输出齐备，所有范围项都有结果，重要问题可追踪，架构与代码质量有独立结论，未执行的模型/人工/设备/发行证据已列明。审查可以得出未通过或证据不足；完成审查不代表问题已修复或项目已验收。

整改另列任务，顺序通常为：P0 数据/安全 → P1 核心链与共享契约 → 各产品缺陷 → 性能/体验 → 清理优化。阻塞后续方向的问题按 4.1～4.3 提前交付和修复，不必等 Q7；其余问题形成后续批次。共享 schema/注册表/跨产品协议先以独立基础提交串行集成，产品修改再更新基线。每项修复保留修改前证据，在实际集成 SHA 上复验原反例、相关下游和必要质量门；合并、部署、发行和人类接受仍各自取得证据。

本计划文档自身的完成条件：范围、任务、G1 判据和并行/合并边界可执行，引用与文档登记有效，未将任何计划项误记为审查通过。计划修订完成后的下一步是 Q0，启动状态仍待用户明确指令。
