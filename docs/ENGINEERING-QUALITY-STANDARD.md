# StoryForge 工程与发布质量标准

> 版本：1.0.0 · 生效：2026-08-26 · 权威层级：L1
> 本标准定义“可以进入 main”的最低条件。它可以被提高，不能被产品任务临时降低。

## 1. 质量模型

| 维度 | 必须证明 |
|---|---|
| 产品正确性 | 行为符合总纲和产品契约，真实用户任务端到端完成 |
| 架构完整性 | 无平行 AI/DB/上下文/生命周期入口，三注册表闭环 |
| 数据安全 | 迁移、刷新、导入导出、删除、作用域和并发不丢失/串改 |
| AI 可靠性 | 合同、预算、schema、stale、恢复、停止和证据可执行 |
| 一致性 | 事实、关系、时间、主支线和作者修改进入正确下游 |
| 可用性 | 加载、空态、错误、取消、键盘/焦点和移动布局可用 |
| 性能 | 大项目下交互、检索、存储与构建不跨越声明预算 |
| 安全与隐私 | Key、手稿、日志、导出与外部请求边界清楚 |
| 可维护性 | 单一职责、显式契约、无死代码、无重复旧入口 |
| 可发布性 | CI、必要 E2E、构建、文档和发布元数据一致 |

## 2. 变更分级

- **低风险**：纯样式、文案、无数据状态的局部 UI。定向检查 + 类型 + 构建。
- **中风险**：领域逻辑、AI 辅助、状态、路由、现有表读写。定向正反例 + 架构门 + 完整 CI。
- **高风险**：schema/迁移、导入导出、删除、版本封存、跨产品引用、正式 AI 写回、认证或发布。必须有生命周期/故障注入/旧数据验证、完整 CI 和隔离 E2E。

风险按影响上调，不因 diff 小而下调。

## 3. 架构门

任何产品增量必须证明：

1. 唯一入口和旧入口下线；
2. AI 读取来自 `CONTEXT_SOURCES`；
3. AI 正式写入来自 Field/Adoption；
4. 表由 `PROJECT_TABLES` 覆盖；
5. 正式模型调用已登记并符合其边界；
6. 产品 owner、世界版本、媒资归属和运行阶段无混淆；
7. 未使用组件内恢复、隐藏重试或并行字段清单。

架构检查器发现的例外必须是窄范围、带理由、负责人和退出条件的代码化允许项。

## 4. 测试金字塔

- 纯函数/类型/schema：快速单元与属性边界。
- 领域服务：正常、空值、冲突、stale、权限、作用域和幂等。
- 数据生命周期：迁移、往返、删除、重映射、blob/OPFS、事务失败。
- Agent/Harness：contract、manifest、结构 repair、预算、checkpoint、receipt。
- 组件：用户事件和可见结果，不只断言内部状态。
- E2E：隔离数据库中的关键产品纵切面、刷新恢复、真实 API（需要时）与跨产品版本引用。

测试必须能在干净环境重复运行；禁止依赖顺序、作者 localStorage、现有 IndexedDB 或线上不可控状态。

Node 测试环境的 fake-indexeddb 6.2.5 会在内部调度数组保留已结束事务，并在后续调度时扫描这些历史条目（[上游实现](https://github.com/dumbmatter/fakeIndexedDB/blob/master/src/lib/Database.ts)）。全局测试 setup 使用具名、锁定版本和内部结构检查的生命周期辅助器，只移除 `finished` 调度条目，保留 active/inactive/committing 及其顺序；不移除业务表、运行事件或回执，不改生产 IndexedDB，也不修改共享依赖文件。版本或内部结构改变须失败并重新审查。公开 IDB 的串行/并发、commit、abort、错误回滚、版本阻塞、删除重建和清理恢复须与未处理的新 Factory 对照验证；不能靠放宽超时或减少原测试内容处理性能失败。

## 5. AI 测试诚实边界

- mock 测试证明协议和控制流，不证明文学质量或供应商兼容。
- 真实 API 测试记录 provider/model、输入契约、原始输出、解析/修复和用量；不得提交 Key。
- 同一模型的一次成功不能代表全部模型。
- 自动 verifier 与 generator 质量分开报告；不能让模型给自己打分后宣称通过。
- 文学质量以预注册维度、盲评/人工抽检和真实长程创作观察补充，不能用编译/测试绿替代。

## 6. 数据质量门

高风险数据变更至少覆盖：空库、当前库、受支持旧库、损坏/缺字段记录、导出导入往返、ID 冲突、删除级联、世界/作品/实例隔离、事务失败和恢复。无法证明不丢数据时不得合并。

备份格式必须带 schema/app 版本和校验；导入先验证再提交。不可恢复操作要有明确用户确认和可下载备份。

## 7. UI 与可访问性

- 所有异步动作有 loading、成功、失败、取消/重试和防重复提交。
- 候选与已采纳内容视觉区分；stale、来源版本和作用域对用户可见。
- 表单有 label、错误定位、键盘可达、焦点恢复和合理 aria。
- 空项目、缺世界版本、无 API、provider 错误、超预算和离线状态都有可行动提示。
- 关键流程在目标桌面宽度与移动窄屏不遮挡数据或操作。

## 8. 性能与规模

性能门使用可重复夹具和声明设备环境。至少关注：启动/升级、列表与检索、Context Gateway、长文本编辑、自动保存、导出导入、build 大小和上层运行回合。

不得只靠提高模型上下文窗口掩盖检索问题；也不得为小数据优化破坏百万字规模下的索引与增量计算。超过预算时先定位 CPU、内存、IndexedDB、网络或模型瓶颈，再决定优化。

## 9. 安全与隐私

- Key 默认只存用户选择的本地配置；日志、截图、错误上报和导出必须脱敏。
- 外部请求只发送任务需要的上下文，Context Manifest 可解释实际来源。
- 导入内容、模型输出、Markdown/HTML、文件名和 URL 均视为不可信输入。
- 在线、社区、支付和远程执行能力在显式授权前 fail closed。
- 依赖公告需要评估可利用性和运行边界，不自动用破坏性升级修复。

## 10. 文档质量

产品边界变化先改总纲/产品契约，代码事实变化同步架构、能力基线、AI Manual 和路线图。完成报告不长期充当规范；历史证据进入 Git/PR/WPS 归档。

所有现行链接必须存在，数量事实尽可能由脚本生成。文档不得宣称未由测试或真实体验证明的“完整”“商业级”“百万字一致”等结果。

## 11. 合并前命令

定向验证后，交付单元运行：

```bash
npm run ci
```

`npm run ci` 应覆盖 required tables、AI Manual、AI 入口、架构、源码可达、路线图、Agent 上下文/freshness、Canon 覆盖、项目指标、依赖审计、lint、TypeScript、覆盖率测试、生产构建与 bundle 门。

适用时再运行：

```bash
npm run ci:e2e
```

CI 任何一步失败都不得称为“全绿”。上游依赖服务阻塞要单独记录，不能吞掉其余门。

## 12. Definition of Done

完成必须同时满足：产品目标达成；范围外未暗中扩张；旧入口删除；数据与 AI 闭环完整；错误与恢复可用；正反例通过；必要 E2E 通过；文档与版本同步；diff 无空白错误；PR 可审查；主干可构建部署。
