# StoryForge Agent 与 Harness 质量标准

> 版本：1.4.0 · 生效：2026-09-28 · 权威层级：L1
> 适用于分步骤长篇、节点、短篇、改编、世界引擎创作和上层产品生产/运行中的正式模型调用。

## 1. 目标与非目标

Harness 的目标是让一次 AI 工作可授权、可恢复、可停止、可追溯、可验证和可安全采纳。它不承诺某个随机模型每次写出优秀文学，也不以增加 Agent 数量作为质量证明。

模型负责开放式语义工作；确定性系统负责 schema、权限、作用域、预算、状态机、幂等、事务、版本、stale、引用和验证。二者边界必须可测试。

## 2. 正式运行最小闭环

```text
产品入口与用户意图
→ 登记的主 Agent / Skill / workflow
→ Run Contract
→ Context Manifest / Gateway
→ 模型与闭集只读工具
→ 原始响应留存
→ 结构归一化与协议校验
→ CreativeArtifact 候选
→ 确定性检查 / 最多一次定向 repair
→ 作者预览、编辑、采纳或拒绝
→ adopt() 与事务
→ post-state 回读
→ terminal receipt
```

任何正式入口缺少其中一环，都必须在 AI 入口注册表中声明有限边界，不能暗示拥有完整 Harness。

## 3. Run Contract

运行开始前冻结：

- 产品、任务、Skill/workflow 与版本；
- project/world/work/product instance 作用域；
- 必需/可选上下文源和最小充分条件；
- 允许工具与写入目标；
- 输入 revision、来源版本与候选 stale 规则；
- 模型路由、上下文/输出/调用/费用预算；
- 状态机、恢复策略、完成判据和最大修复/重试次数。

运行中不能由模型扩大权限、创造未登记工具或把辅助结果升级为正式写入。

Instance-owned 运行创建可携带 `expectedRuntimeSessionHash` 前置条件：产品先完成自己的来源/权限读取，创建事务再核对整个原实例记录的 canonical hash，匹配后才写 Run/事件。它是防止取消、删除或其他实例变化穿过“最后一次读取 → 创建”的原子边界，不能代替产品授权。该值在首次 await 前固定，不进入 RunContract 或备份身份；省略它的既有调用与原合同/hash 保持。失败不创建半个 Run，也不借此自动重读来源或重发模型。

零模型的确定性提交可在 V1 终验回执中使用显式 `zeroModelCommit` 扩展：保留原 canonical RunContract、非空准确输入工件引用与实际 post-state/验收依据。仅合同的模型与输入/输出 token 预算全为零、Context/Skill/写回权限为空，且无候选、采用或语义评审时，才允许空 `contextManifestHashes`；合同正文 hash 必须匹配回执合同 hash。不得伪造一份模型 Context Manifest 来完成人工记账。普通模型回执仍保持原非空来源约束，旧回执/hash 不补字段。零模型记录完成只证明确定性提交，后续模型 lineage 必须另冻目的、来源、profile/transport、预算与用户授权。

音频候选的正式入口显式冻结 `outputModality:'audio'`；省略该字段的历史文本入口保持原字节与 hash。音频绑定只允许无只读工具、无正式写目标、无自动采用的产品运行候选，经独立冻结执行器核对 Skill、category、实际 caller 和取消后调用产品传输，不能借用 Chat/流式文本执行器。产品仍负责原请求谱系、发送前持久 attempt、离线/预算约束和原始响应；音频时长、字节、字符与实际模型调用分别计量，不能把文本窗口估算当成实际语音 token 用量或捏造费用。原始返回留存也不等于音频候选通过验证。

音频使用显式 `CreativeAudioArtifactV1` 引用合同：原输入、真实 Context Manifest 和原始响应的准确 hash，加上实际音频描述、检查问题与原请求证据。一次 durable 音频请求可能包含多段实际编码/合成，`requestEvidence` 不冒充一次物理模型调用；真实次数与音频用量由产品原输出证据核验，不填造文本 token。大音频留在原 exact artifact/产品 Blob 生命周期中，不复制进文本 V1 的 `originalText/editableText`，不裁剪原始响应。纯合同解析不证明 PCM 正确、owner/权限或真人听感，产品须另核验真实原证据与字节。候选固定 `humanListening:'unproven'`、`adoptionAllowed:false` 与禁止自动重试；试听与正式采用由产品沿原 owner 独立确认。旧文本 V1 解析/字节不变，文本采用判断不接受音频合同，不能把音频 `ready` 当作授权。

## 4. 渐进式上下文披露

上下文分层保存与读取：

1. 原文和用户输入，永久保留其来源；
2. 结构化事实、实体、关系、事件、主支线、版本；
3. 可重建摘要和索引；
4. 当前任务目录、硬约束和预选结果；
5. 按需读取的详情与原文证据。

Context Gateway 应先给 Agent “能读什么”的目录，再根据任务、实体、时间、故事线与证据需要加载内容。必须记录：候选来源、选择理由、实际读取、hash、token 估算、被排除来源与不足状态。

固定前缀、固定条数和 token 截断只在最后保护预算。晚出现、低频但关键、被标记为伏笔或用户锁定的事实必须有独立召回路径。

## 5. 结构化输出与修复

- 输出契约使用 schema 和稳定字段，不依赖“请返回合法 JSON”一句话。
- 保留原始响应；解析失败不得覆盖原文。
- 可容错提取只用于找回明显可识别字段，结果仍需完整 schema 校验。
- 只有定位到确定性、可修复问题时最多执行一次定向 repair；repair 输入包含错误路径而不是重做全部创作。
- 相同错误、权限/余额/限流/非重试 4xx、stale、结果未知或预算不足必须停止并向用户说明。
- 超长输出按用户显式长度合同处理；默认长度是产品策略，不是硬编码模型极限。

## 6. 候选、版本与 stale

候选至少保存：原始输出、编辑稿、输入 manifest hash、目标 revision、模型/Skill/Prompt 版本、问题、用量、修复记录和创建时间。

发生以下任一变化应 stale：目标字段、关键上下文 revision、锁定世界版本、产品配置、上游已采纳产物或作用域。stale 候选仍可查看和复制，但不得直接采纳。

刷新后候选、采纳/拒绝状态和运行证据必须从持久化恢复，不依赖 React 内存。作者手工修改必须马上进入 revision 体系。

## 7. 扩写、重写与润色

- `expand`：以增加内容为目标；界面至少展示原版与新版，可提供结构/段落级对照。是否做事实级硬验证由产品风险决定，默认不把创意差异误判为失败。
- `rewrite`：允许整体重构，直接交付新候选；不得伪装成保留原文事实的操作。
- `polish`：优化表达、逻辑和节奏；应展示前后版本，方便作者判断是否接受。
- 用户补充说明、当前字段、关联上下文与 Prompt 版本都必须进入候选证据。

事实级比较和语义差异 UI 可以作为辅助，不得通过字符 diff 冒充文学语义验证。

## 8. Durable 状态与恢复

运行账本至少覆盖：created、planned、running、waiting-author、repairing、adopting、completed、rejected、failed、cancelled 和 stale。状态转换必须单调、幂等并有事件证据。

- 每个外部调用前后保存 checkpoint/attempt identity。
- 网络结果未知时不盲目重复可能产生费用或重复写入的调用。
- 恢复时校验 contract、执行版本、来源/目标 revision 和既有回执。
- Instance-owned 检查点核验及恢复开始/完成显式传入 `productRuntimeSessionId`，沿用创建时的实例事务与精确 owner 核对；缺失或不同实例拒绝，错误不留下半个恢复事件。省略参数的 Work 路径继续保留原事务表集合和原合同/检查点 hash，不把实例表偷偷加入作者的既有子事务。
- 终态只有在完成判据和 post-state 证据满足后成立；UI 显示完成不能替代 durable receipt。
- 离线核验历史终态的记忆结算时，可将已验证的原合同、事件、投影、创建时间与冻结的 World/Work code 传给同一结算投影器；不得用导入后的当前身份替换原身份。该只读路径不查当前身份行、不生成结算事件、不创建或恢复 Run，也不授予采纳权限；原在线路径的字段、身份读取与回执 hash 保持不变。历史账本与冻结身份的完整性由调用方先行验证。

## 9. 多 Agent 与自主生产

用户面对产品主 Agent；内部专业 Agent/Skill 只有在任务可独立、输入输出契约明确且能带来质量或延迟收益时拆分。主 Agent 应冻结计划、依赖、预算和验收，专业分支返回受类型约束的产物。

不要为组织形式本身增加 Agent。能由一次高质量模型调用加确定性验证完成的任务，不强制多轮互相总结。并行只用于真正独立的内容、规则和媒资生产，合并点必须有版本与冲突检查。

## 10. 长篇规模门

“理论支持百万字”必须同时具备：

- 原文、事实、关系、时间线、主支线、章节和运行历史分层持久化；
- 稳定资源 ID、revision 和来源证据；
- 目录 → 预选 → 按需详情/原文的检索链；
- 长尾、晚出现、跨世界/作品隔离与伏笔反例；
- 章节生成、采纳、后处理、下游演化的 durable lineage；
- 在 10 万、30 万、100 万字符/等价规模夹具上的召回、预算和性能门；
- 真实模型主路径与人工抽检。

通过合成规模测试只能证明工程链可扩展，不能证明百万字文学一致性已经解决。能力基线必须区分“基础设施存在”“纵切面跑通”“真实长期创作验证完成”。

当上述工程门和真实模型主路径均有证据时，可以把“理论工程支撑百万字符级创作”登记为已完成能力；真实作者长期文学一致性是另一层持续质量认证。后者没有结束，不得反向把已经验收的 Harness 主链和工程规模门重新标成未完成功能。

## 11. 世界衍生产品

上层产品遵守项目三阶段主链：

- `S1 世界封存`由世界引擎封存不可变语义版本；
- `S2 产品定向`由具体产品在用户选定冻结世界版本后生成并校验 WorldReference、收集产品专用设置、完成意图会谈，并在用户明确开始时冻结 WorldReference、Brief 与 SourcePlan；
- `S3 产品执行`由具体产品完成 S3.1 生产、S3.2 验收、S3.3 发布、S3.4 运行与演化；每个 run 只在 SourcePlan 锁定的世界版本与权限内渐进读取并保存不可变 Context Manifest，发布时聚合为 ProductSourceManifest。runtime 后续读取归 session/run 证据，不修改旧 release。

Harness 不统一时长、章节、结局或演化触发字段；它只执行产品已经定义的 Run Contract。任何长时或开放式体验仍须由一系列有限、可停止、可保存、可恢复的 durable run 组成，不能用一个永不结束的模型调用实现。运行绑定 ProductRelease，结果不得写回世界引擎。

生产时 AI 与运行时 AI 使用不同授权边界。允许运行时模型参与的产品必须冻结 Runtime AI Contract：可读 release/session 来源、可写私域状态、禁止边界、工具闭集、预算/时延、provider 能力、失败/离线降级、持久化、审计、回滚和存档兼容。模型不能扩大 SourcePlan、修改 WorldRelease/ProductRelease 或接管确定性状态机。

Harness receipt 只能证明相应 run 和控制流完成，不能自行提升作品的验收成熟度。`engineering-playable`、`creator-accepted`、`player-validated` 和 `distribution-ready` 必须引用各自所需的自动、创作者、独立玩家和权利/分发证据；自动 verifier、generator 自评或已知路线通关不能替代真人体验。

## 12. 验收证据

每个 Skill/入口至少有：正常、空上下文、stale、非法结构、超长输出、预算不足、provider 错误、刷新恢复、拒绝、采纳、下游生效和作用域隔离测试。正式入口还需通过 AI 入口扫描、Skill freshness、三注册表守卫和必要 E2E。
