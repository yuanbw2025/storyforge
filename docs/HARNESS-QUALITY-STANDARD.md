# StoryForge Agent 与 Harness 质量标准

> 版本：1.1.0 · 生效：2026-08-27 · 权威层级：L1
> 适用于分步骤长篇、节点、短篇、改编、世界引擎创作和上层产品生产/运行中的正式模型调用。

## 1. 目标与非目标

Harness 的目标是让一次 AI 工作可授权、可恢复、可停止、可追溯、可验证和可安全采纳。它不承诺某个随机模型每次写出优秀文学，也不以增加 Agent 数量作为质量证明。

模型负责开放式语义工作；确定性系统负责 schema、权限、作用域、预算、状态机、幂等、事务、版本、stale、引用和验证。二者边界必须可测试。

## 2. 正式运行最小闭环

```text
产品入口与用户意图
→ 登记的主 Agent / Skill / workflow
→ Run Contract
→ Context Manifest / Gateway
→ 模型与闭集只读工具
→ 原始响应留存
→ 结构归一化与协议校验
→ CreativeArtifact 候选
→ 确定性检查 / 最多一次定向 repair
→ 作者预览、编辑、采纳或拒绝
→ adopt() 与事务
→ post-state 回读
→ terminal receipt
```

任何正式入口缺少其中一环，都必须在 AI 入口注册表中声明有限边界，不能暗示拥有完整 Harness。

## 3. Run Contract

运行开始前冻结：

- 产品、任务、Skill/workflow 与版本；
- project/world/work/product instance 作用域；
- 必需/可选上下文源和最小充分条件；
- 允许工具与写入目标；
- 输入 revision、来源版本与候选 stale 规则；
- 模型路由、上下文/输出/调用/费用预算；
- 状态机、恢复策略、完成判据和最大修复/重试次数。

运行中不能由模型扩大权限、创造未登记工具或把辅助结果升级为正式写入。

## 4. 渐进式上下文披露

上下文分层保存与读取：

1. 原文和用户输入，永久保留其来源；
2. 结构化事实、实体、关系、事件、主支线、版本；
3. 可重建摘要和索引；
4. 当前任务目录、硬约束和预选结果；
5. 按需读取的详情与原文证据。

Context Gateway 应先给 Agent “能读什么”的目录，再根据任务、实体、时间、故事线与证据需要加载内容。必须记录：候选来源、选择理由、实际读取、hash、token 估算、被排除来源与不足状态。

固定前缀、固定条数和 token 截断只在最后保护预算。晚出现、低频但关键、被标记为伏笔或用户锁定的事实必须有独立召回路径。

## 5. 结构化输出与修复

- 输出契约使用 schema 和稳定字段，不依赖“请返回合法 JSON”一句话。
- 保留原始响应；解析失败不得覆盖原文。
- 可容错提取只用于找回明显可识别字段，结果仍需完整 schema 校验。
- 只有定位到确定性、可修复问题时最多执行一次定向 repair；repair 输入包含错误路径而不是重做全部创作。
- 相同错误、权限/余额/限流/非重试 4xx、stale、结果未知或预算不足必须停止并向用户说明。
- 超长输出按用户显式长度合同处理；默认长度是产品策略，不是硬编码模型极限。

## 6. 候选、版本与 stale

候选至少保存：原始输出、编辑稿、输入 manifest hash、目标 revision、模型/Skill/Prompt 版本、问题、用量、修复记录和创建时间。

发生以下任一变化应 stale：目标字段、关键上下文 revision、锁定世界版本、产品配置、上游已采纳产物或作用域。stale 候选仍可查看和复制，但不得直接采纳。

刷新后候选、采纳/拒绝状态和运行证据必须从持久化恢复，不依赖 React 内存。作者手工修改必须马上进入 revision 体系。

## 7. 扩写、重写与润色

- `expand`：以增加内容为目标；界面至少展示原版与新版，可提供结构/段落级对照。是否做事实级硬验证由产品风险决定，默认不把创意差异误判为失败。
- `rewrite`：允许整体重构，直接交付新候选；不得伪装成保留原文事实的操作。
- `polish`：优化表达、逻辑和节奏；应展示前后版本，方便作者判断是否接受。
- 用户补充说明、当前字段、关联上下文与 Prompt 版本都必须进入候选证据。

事实级比较和语义差异 UI 可以作为辅助，不得通过字符 diff 冒充文学语义验证。

## 8. Durable 状态与恢复

运行账本至少覆盖：created、planned、running、waiting-author、repairing、adopting、completed、rejected、failed、cancelled 和 stale。状态转换必须单调、幂等并有事件证据。

- 每个外部调用前后保存 checkpoint/attempt identity。
- 网络结果未知时不盲目重复可能产生费用或重复写入的调用。
- 恢复时校验 contract、执行版本、来源/目标 revision 和既有回执。
- 终态只有在完成判据和 post-state 证据满足后成立；UI 显示完成不能替代 durable receipt。

## 9. 多 Agent 与自主生产

用户面对产品主 Agent；内部专业 Agent/Skill 只有在任务可独立、输入输出契约明确且能带来质量或延迟收益时拆分。主 Agent 应冻结计划、依赖、预算和验收，专业分支返回受类型约束的产物。

不要为组织形式本身增加 Agent。能由一次高质量模型调用加确定性验证完成的任务，不强制多轮互相总结。并行只用于真正独立的内容、规则和媒资生产，合并点必须有版本与冲突检查。

## 10. 长篇规模门

“理论支持百万字”必须同时具备：

- 原文、事实、关系、时间线、主支线、章节和运行历史分层持久化；
- 稳定资源 ID、revision 和来源证据；
- 目录 → 预选 → 按需详情/原文的检索链；
- 长尾、晚出现、跨世界/作品隔离与伏笔反例；
- 章节生成、采纳、后处理、下游演化的 durable lineage；
- 在 10 万、30 万、100 万字符/等价规模夹具上的召回、预算和性能门；
- 真实模型主路径与人工抽检。

通过合成规模测试只能证明工程链可扩展，不能证明百万字文学一致性已经解决。能力基线必须区分“基础设施存在”“纵切面跑通”“真实长期创作验证完成”。

## 11. 世界衍生产品

上层产品遵守项目三阶段主链：

- 阶段一由世界引擎封存不可变语义版本；
- 阶段二由具体产品读取 WorldReference、收集产品专用设置、完成意图会谈，并在用户明确开始时冻结 Brief 与 SourcePlan；
- 阶段三由具体产品完成 production、内容/规则/媒资、组装、质量修复、ProductRelease、运行和私域演化；每个 run 只在 SourcePlan 锁定的世界版本与权限内渐进读取并保存不可变 Context Manifest，发布时聚合为 ProductSourceManifest。runtime 后续读取归 session/run 证据，不修改旧 release。

Harness 不统一时长、章节、结局或演化触发字段；它只执行产品已经定义的 Run Contract。任何长时或开放式体验仍须由一系列有限、可停止、可保存、可恢复的 durable run 组成，不能用一个永不结束的模型调用实现。运行绑定 ProductRelease，结果不得写回世界引擎。

## 12. 验收证据

每个 Skill/入口至少有：正常、空上下文、stale、非法结构、超长输出、预算不足、provider 错误、刷新恢复、拒绝、采纳、下游生效和作用域隔离测试。正式入口还需通过 AI 入口扫描、Skill freshness、三注册表守卫和必要 E2E。
