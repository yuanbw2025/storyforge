## 3. 每个功能怎样才算走完

### 3.1 有生成按钮的功能

1. 打开空数据和已有数据两种状态，记录当前正式内容及受保护区域哈希。
2. 填写实际支持的参数；分别覆盖必填、留空、中文输入、取消和边界值。
3. 依次运行该入口支持的生成/扩写/重写/润色，记录真正模型请求、上下文和运行终态。不能用一个字段的结果替代其它入口。
4. 修改候选，先试非法结构/枚举/引用，再纠正；确认编辑候选时正式数据没有变化。
5. 拒绝一次候选，确认正式内容不变；再次生成并明确采纳，检查实际写回和 receipt。双击不能重复写，旧候选不能覆盖新稿。
6. 再手改正式内容，包括清空、长文本和中文组合输入；分别核对实际存在的自动保存、失焦保存、显式保存。
7. 切到其它步骤再返回、硬刷新、关闭并重启客户端，逐字段比对文字、顺序、角色/地点引用和保存状态。
8. 真正打开下游并生成下一步：核对 Context Manifest 引用的是本次已保存/采纳的内容和正确 owner，不只检查页面上看得到。
9. 在关键时点取消、断网、切章/切作品、刷新、注入写入失败和 stale，恢复后继续原流程；保留原始失败，不以重试成功抹掉第一次失败。

正式生成入口及其支持模式都必须取得真实 Agnes 成功链证据；受控响应可用于穷举协议反例。**Mock UI、真实模型、原生包和升级证据分开记，互不替代。** 不能通过改小候选、降低校验、吞错或关掉功能让测试变绿。

### 3.2 没有生成按钮的功能

手工表单按“新建/输入→修改/清空→保存→切页→刷新/重启→下游”验收。只读关联预览、用量统计按“打开→数据准确→刷新→跳转→失败提示”验收，不虚构生成/采纳按钮。删除、排序、复制、批量、导入和恢复各自另走确认与取消分支；矩阵中的“展开清点”必须派生这些具体用例后才能完成。

结构化条目逐个手改每个子字段；若 AI 只生成整条候选，就按整条生成/采纳、逐子字段回读，不能声称每个子字段都有独立 AI 入口。同一共享组件在不同入口仍要各走一次，避免漏掉参数、scope 和加载时机差异。

### 3.3 字段回读与坏数据处理

“保存成功”必须有持久层读回，且新浏览器上下文/客户端重启后仍一致。候选采纳前、拒绝后和失败后对比正式手稿哈希；采纳后对比候选编辑器、正式记录和下游读取。适用的来源、owner、引用、版本、stale 和事务必须一并验证。

坏字段可以暂时阻断依赖它的正式生成，但应保留原始记录、定位问题并提供明确修复/恢复路径。空数据正常提示、结构损坏和加载失败必须区分；不能把读取异常伪装成“没有数据”，更不能保存空数组覆盖原稿。

### 4.3 清单保持完整的规则

进入每页后同时盘点：标签、折叠项、更多菜单、空/有数据状态、弹窗、快捷操作、禁用与错误状态。每个可操作控件必须映射到已有 case 或新增 case；每个 case 必须反向指向真实入口。发现漏项追加稳定编号，不删失败项、不重置统计。动态列表按元素类型参数化，同时保留新增、编辑、删除、引用、排序等不同动作的独立结果。

## 6. 数据、模型、故障与平台矩阵

| 维度 | 必测组合 |
|---|---|
| 数据 | 新建空作品；现行正常作品；受支持旧版合成数据库/备份；缺失/null/错误类型/损坏JSON；两作品和两世界；10万/30万/100万字符及大量章/角色 |
| 模型 | 现行 Agnes 正式链；受控空响应、截断、非法schema、流中断、401/403/429/5xx、非重试4xx、余额/授权和结果未知；保留每次请求与重试用量 |
| 保存时点 | 中文输入组合中、失焦前后、自动保存前后、显式保存、切页/切章/切作品、刷新、关窗口、重启、双标签竞争 |
| 文件 | JSON完整往返；TXT/Markdown正文；TXT/Markdown/DOCX导入；备份恢复、磁盘/权限失败、冲突、引用重映射、删除取消与确认 |
| 客户端 | Windows安装版/便携版优先；Android触屏/后台/内存压力；macOS和浏览器；Linux与受支持浏览器主链。记录真机/模拟器/CI与精确包，不混为同一证据 |
| 连续使用 | 同一作品至少两小时，覆盖两卷三十章的推进与回改；生成中切换/取消/恢复、多窗口、长文编辑与导入导出，逐项记录耗时、内存和原文完整性 |

不是把所有维度机械相乘：每个功能都走正常全链和该入口的保存/切换反例；共享协议故障以组件/Skill绑定参数化穷举；正文、采纳、批量、导入导出、恢复、跨作品边界必须跑完整高风险集合。共享实现通过不能抵消某个入口失败。

需要实体平台、服务或私有配置但尚未获得的证据标 `BLOCKED` 并写缺口，不能拿 Mock 或其它平台代签。第三方云备份/社区发布使用隔离账号或受控端点，不向真实作者账号上传测试内容、不实际发布作品。没有外部正式上传授权不阻断本地可继续的修复；对应外部验收仍保持未完成。

## 7. 每个问题如何修、如何留证

1. 先保留原错误、精确版本/入口和合成最小复现；区分产品缺陷、环境依赖不足、受控预期拒绝和证据不足。
2. 关联已有 GitHub Issue；后台私有问题按 `COLLAB-WORKFLOW.md` 脱敏整理。新公开工单/评论遵守用户的消息发送授权；未获授权时先保留可审阅技术草稿，不以发送为本地修复前置。
3. 沿“入口→注册读取→候选/写回→生命周期→下游→测试”定位，先写真正能失败的定向回归，做保留架构的最小修复；避免只 catch 后返回空数据。
4. 用原失败输入复测，再走该功能完整链和共享调用方回归；有 schema/迁移/删除/导入/恢复时做隔离数据往返与反例。
5. 修复提交前按 AGENTS 和现行质量标准完成适用检查；交付代码单元运行 `npm run ci`，真实 UI/API/恢复路径运行隔离 `npm run ci:e2e`，不改作者项目。当前计划文档只做直接文档、清单与链接检查，不宣称产品 CI 已通过。
6. 记录实际最终 SHA、构建版本、包哈希、平台、fixture、模型/模拟方式、操作预期与观察、字段回读/保护哈希、manifest/receipt、异常与请求/用量、关联 Issue/PR、发行状态。原始敏感材料只在私有目录。
7. 通过审查后小批交付；已有发行机制管理安装包和更新。逐个平台安装包含该修复的精确包，重复原场景；旧版异常与新版复发分别计数。合并、发行和用户侧观察是不同状态。

优先级：P0 为丢稿/错写他作/数据不可恢复；P1 为白屏或无法生成、采纳、保存、恢复等主链阻断；P2 为可恢复但影响操作的提示、布局或性能问题。发现 P0/P1，暂停该范围推进，先保留证据并修复，其它独立范围可继续。

## 8. 进度怎样给用户看

每次进度给出：新增实际走完哪些功能、正常/异常路径通过多少、发现/修复哪些问题、仍有哪些失败、下一个单元、当前是否进入正式安装包。展示“清点、待测、执行中、通过、失败、外部阻塞、明确不适用”；不把代码行数、测试数量、PR 数当用户流程完成率。

一个 case 只有其全部适用操作、字段、模式、故障和派生子用例都有本轮成功回执才可 `PASS`。不适用必须注明真实能力和依据。`DISCOVER` 的完成只说明清点结束，需列出派生 case；它不能算成完整功能通过。统计同时公布功能全链、字段、故障、平台和发行状态；分母增加时保留原因。

现有自动化测试只作为候选入口：`longform-browse`、`longform-integration`、`longform-chapter-draft-save`、`longform-step-quality`、`longform-selected-revision`、`longform-memory-json`、`codex-authoring`、`docx-import-compat`、`failure-reporting`、`client-support` 等。开工时先读当前断言与真实动作，补缺并重跑；不能仅因文件存在就认定覆盖。
