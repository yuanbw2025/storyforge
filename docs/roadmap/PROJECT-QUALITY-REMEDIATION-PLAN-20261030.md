# StoryForge 架构与质量整改推进方案

> 版本：1.0.2 · 生效：2026-10-30 · L2 整改施工计划
> 状态：规则和任务编排已形成；产品实现整改尚未验收，G1 未放行，稳定底座 B 尚未建立。
> 问题依据：[全项目审查](../audits/PROJECT-QUALITY-AUDIT-20261029.md)及[审查计划](../audits/PROJECT-QUALITY-AUDIT-PLAN-20261029.md)；上位约束为总纲、数据治理、工程质量标准与协作流程。
> 机器任务清单：[quality-remediation-tasks-20261030.json](./quality-remediation-tasks-20261030.json)。144 项问题各有唯一主任务；同根子入口继续保留，不能只修一个入口便关闭整项。

## 1. 目标与推进原则

先消除会造成数据损失、越权读取、授权失真、隐式重发和不可恢复的风险，再建立可供后续开发使用的、范围明确的稳定底座。结构清理继续完成，但不以所有 P2 清零作为每个产品开工的前置。

采用“方案约束 + 小修复单元 + 多代理并行 + 共享底座串行集成”。各轮是依赖与风险分组，不是必须全项目等齐的日历批次。某产品的依赖修复和验证完成后即可单独申请 G1；其它产品仍未通过的范围保持关闭。低风险、无共享依赖的任务可以提前，不挤占止损修复与复审容量。

本方案不把 144 项打成一个 PR，不重建第二套 AI、数据库、上下文、恢复或产品状态机。任何清理先证明行为及兼容性，再移除真实失效入口；历史 Release、存档、候选和回执的读取分支不能仅因“看起来旧”被删除。

## 2. 已确认的世界来源规则

用户于 2026-10-30 明确裁决 SFQA-005：文字开放世界不得直接以小说固定版本或小说私有 SourcePin 作为正式来源。小说来源必须经过以下链路：

```text
小说 Work 的已确认内容
→ 作者显式派生独立 World 草稿（保留范围、revision、hash、来源权利与 lineage）
→ 作者检查并确认世界语义
→ 世界引擎封存不可变 WorldRelease
→ 文字开放世界 S2：选定版本、定向、冻结 Brief / SourcePlan 并明确开始
→ S3：生产、质量检查、ProductRelease、运行
```

已有合法 WorldRelease 可直接进入 S2，不要求再找一部小说。小说 owner 不变；派生后双方修改不自动同步。World 只拥有语义；文字开放世界拥有自己的生产、媒资、发布、Session 和私域演化。

SourcePin 仍可作为产品内部的冻结读取证据或历史格式，不能替代 WorldRelease 身份。复用现有 `deriveNovelToWorld` 和世界封存能力；本产品快捷入口必须先派生草稿并展示确认，不以自动复制、立即封存冒充作者检查。不得为纠偏全局破坏其他独立产品的合法改编来源。

### 2.1 历史兼容与准入分离

| 对象 / 动作 | 整改后的规则 | 必须证明 |
|---|---|---|
| 新来源选择、Brief 模型会谈、正式开始 | 必须绑定真实 WorldRelease；选择小说时引导派生和封存 | 未封存、篡改、跨 owner、权利不符均在调用/写入之前拒绝 |
| 新生产、继续制作、子 Build 返修、媒资重做、新发布 | 统一受新准入约束；旧小说 SourcePin 不能继续充当来源授权 | 服务、刷新恢复、后台命令与 UI 一致，拒绝时零模型/媒资发送、零正式写入 |
| 旧 SourcePin、Build、Release、Session、回执和备份 | 保留原字节、hash、原 lineage；允许核验、只读浏览、历史回放、导出和旧证据恢复 | 不改写为伪造 WorldReference；合法备份往返仍可读取 |
| 旧小说来源 Release 新开局或新增互动事件 | 不因 codec 能读就默认获得授权；本次兼容范围限于只读与历史回放 | 新 Session、续玩写事件及新生产入口均有确定性阻断与可行动说明 |
| 需要继续使用旧内容制作或互动 | 作者显式派生/选择封存世界，重新定向、确认授权，形成新谱系 | 新 Release 与旧记录可分别解释，不静默迁移或原地补改旧 hash |
| 已绑定合法 WorldRelease 的历史内容 | 保留原有合法路径，依旧受版本、权利、来源和质量门约束 | 正常制作/发布/运行对照不被误伤 |

旧存档向新世界来源 Release 的状态迁移不默认兼容：只有存在已验证的显式迁移合同和作者/玩家确认时才创建新存档；否则保留旧档，只提供新开局。拒绝继续制作时保留未完成任务及已付输出；未知结果不得借纠偏重发。

SFQA-005 的状态是“决策已确认，规范已修订，代码实施与兼容验收待完成”，仍是开放 P1。不能用文档修改关闭问题。

### 2.2 旧备份的歧义章节关联恢复（SFQA-037）

用户于 2026-10-31 明确选择：**先恢复确定内容，完整保留并标出无法确定的关联，之后由作者确认。** 此项已完成策略裁决，代码实施和新旧备份验收仍待完成。

- 歧义记录、原引用值、来源备份身份及判断依据完整保留，并向作者明确展示待确认项；不得猜测归属、静默删字段或把旧数字当作新库的有效章节外键。

## 6. 多代理和工作树协议

默认资源上限：协调者 + 两个实现代理 + 一个独立复审代理。已获得用户并行授权，无需每项重问；仍须检查文件占用与真实任务边界。复审者不同时复审自己写的改动。

- 一个工作树只有一个写入者。新实现从当时最新 C 或明确已验证的依赖提交建立 `fix/` / `refactor/` 分支；计划/报告树不混写产品修复。
- 开工卡列出完整读写文件、owner、注册表行和共享热点。协调者保存认领表；路径或契约重叠时暂停分派，抽取共同基础任务。一个组不获得永久独占，也不能只按目录名推定无冲突。
- schema、三注册表、世界出口、Adoption/Harness 原语、跨产品契约、目录、共享 codec、package/lockfile、CI/静态门、authority 索引由指定唯一任务串行修改。产品代理先使用已接受的接口，不能各写一份临时公共实现。
- 每次返回：分支/完整 SHA、关联问题及子范围、实际路径、验证命令与终态、未完成项、兼容/恢复方式。不得发送作者数据、凭据或完整模型原文到共享消息。
- 定向测试可使用隔离数据库并行；同一机器上的整库 CI、覆盖率和 E2E 依次占用资源。若用独立 runner，同时验证也须保留各自精确 SHA 和结果。
- 合并顺序为治理/准入 → 共享底座 → 产品接入 → 独立清理。每次集成后，后继分支更新明确依赖 SHA，复验受影响调用方；不等到所有功能完成才检查兼容性。

## 7. 每个修复的开工卡与完成标准

```text
任务ID / 原问题ID及全部子入口 / 风险 / 负责人 / reviewer
产品 / 生命周期 / S1-S2-S3位置 / 用户入口与可见结果
起点完整SHA / 治理版本 / 已合入和未合入依赖
owner / 读取来源 / 候选与写回 / 表与schema / 媒资 / 下游
读写路径 / 共享热点认领 / 旧入口与历史兼容
原反例在本起点的结果 / 最小修复 / 正例、反例和故障注入
CI、E2E、真实provider、人工、设备分别需要什么证据
保护和恢复方式 / 精确提交 / PR与合并状态 / 未完成边界
```

状态按“待起点复核 → 可开工 → 实现中 → 待独立复审 → 待集成 → 集成复验 → 已关闭”推进；阻塞必须记录具体条件，不能把等候完整门记为已完成。合并、部署、客户端发行、真人/模型/商业接受分别记状态。

所有代码修复先跑对应正反例；数据/版本/授权变更加并发、中断、stale、跨 Work/World、旧数据与零写入负例。代码提交前至少执行 AGENTS 要求的 `npm run check:architecture`、`npm run check:required-tables`、`npm run check:ai-manual`、`npx tsc --noEmit`、相关测试及 `npm run build`，其余按风险加验；交付单元完整 `npm run ci`，高风险真实路径在独立数据环境完成 `npm run ci:e2e`。仅文档变更执行对应文档检查；新增本方案/清单登记 authority 和 allowlist，不能将文档绿灯当作产品实现绿灯。

完整 CI/E2E 已有失败和跳过的原因须查明，不能统一提高超时、缩小覆盖范围、删断言或靠定向重跑消除原记录。坏断言修复应证明错误实现确实失败、正确实现才通过。每次改变代码后，以最终候选树的验证为准，引用别的树的绿灯须说明适用范围。

关闭一项须满足：所有适用子入口已验收，原反例变为正确行为，正常/兼容对照无回归，下游真实消费，必要门通过，独立复审无未解决高风险意见，代码已进入指定集成提交。只修规范、某个热态入口或 UI 提示，不能关闭整个问题。

## 8. 分范围 G1 与后续开发

每张 G1 卡记录：产品/功能范围、不可变 B SHA、已解决问题及子范围、依赖原语版本、验证证据、未完成事项和到期复核条件。新增需求先映射到原 30 行产品/共享矩阵与任务清单；只解除自己实际依赖的阻塞。

例如：只改不持久化的局部文案可在无共享热点时并行；新的正式 AI 写回必须等相关 owner、配置身份、原响应、采纳、恢复和数据生命周期闭环；开放世界正式扩建还须通过 SFQA-005 的来源/历史兼容纵切面。分支隔离不能替代这些依赖。

G1 不等于产品公开发行或商业验收。真实模型/媒资先固定合成样本、输入、预算和用途；文学/视觉/玩法需独立作者或玩家评价；客户端需实际目标平台安装升级和数据保留；权利证明不得由字节 hash 代替。

## 9. 外部验证与维护观察也不漏项

任务 JSON 同时保留原 8 个验证组：完整质量门、真实 provider、规模/存储、人工/无障碍、客户端设备、权利/供应链、世界规则、主干差异。其中世界规则已由用户裁决，但实现及兼容待验收；主干差异已完成本次去重，下一集成树仍需差异复核。二者均不自动关闭其关联问题。

另有 6 个 Opus 设计/维护风险组：未来库启动恢复、合同期限、缓存预算、暂存 Blob、诊断证据与 i18n。先形成范围和验证决策，不擅自抬成已复现缺陷或删除原保守边界。18 项维护观察中的缺陷外事项继续按原性质跟踪：正面实践保持，纯维护建议评估后进入 R3；不得把它们混算为新增 P1/P2，也不得因不计缺陷而丢弃。

实施期间保持简短进度回执：完成的具体问题、正在处理的唯一任务、下一个依赖、当前门和阻塞。不按修改行数、子代理数量或提交数宣称质量提升；只有可重复的行为、兼容、失败恢复和验收结果可关闭任务。
